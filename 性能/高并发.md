# 高并发：Node.js 与 Java 的两条路

### 先把问题定义清楚
高并发要解决的是：**同一时刻有大量请求积压在系统里**。瓶颈基本不在「CPU 算不完」，而在：

| 瓶颈 | 表现 |
| --- | --- |
| 连接数 | 一连接一线程，几万连接就崩（C10K 问题） |
| 线程开销 | 每线程 1~8 MB 栈 + 内核调度对象 |
| 上下文切换 | 线程数远超核数时，CPU 大量时间在切换而非计算 |
| IO 等待 | 线程阻塞在 socket / 磁盘上，白占资源 |
| 锁竞争 | 共享资源被串行化，加机器也不提速 |

关键公式：`QPS = 并发数 / 平均响应时间`。RT 从 100ms 降到 10ms，等价于机器数 ×10。

### 两种模型的根本分歧
```
同步阻塞：线程 = 请求     →  用「线程数」扛并发，线程贵，数量上不去
事件驱动：线程 ≠ 请求     →  用「状态机 + 回调」扛并发，一份状态几 KB
```

| 维度 | 线程-per-request（传统 Java） | 事件循环（Node.js） |
| --- | --- | --- |
| 并发载体 | OS 线程 | 事件循环里的回调 / Promise |
| 单连接内存 | MB 级 | KB 级 |
| 并发上限 | 几千 | 几十万 |
| 一处阻塞的代价 | 只挂自己这条线程 | 挂掉**整个进程**的所有请求 |
| 多核利用 | 天然 | 需要多进程 |
| 心智负担 | 低（顺序代码），但要加锁 | 高（异步传染），但基本无锁 |

结论先给：**Node 天生适合 IO 密集 + 高连接数；Java 靠线程池 / NIO / 虚拟线程补齐并发能力，换来 CPU 密集场景和生态上的优势。**

## 一、Node.js 如何实现高并发

### 1. 核心机制：单线程事件循环 + libuv 多路复用
```
JS 主线程（单线程，只跑你的业务代码）
   │  发起 IO，注册回调后立刻返回
   ▼
libuv ── 网络 IO ──→ epoll / kqueue / IOCP（内核级多路复用，不占线程）
       └ 文件 / DNS / crypto ──→ 线程池（默认 4，UV_THREADPOOL_SIZE 可调到 128）
   │  IO 就绪
   ▼
事件循环取出回调，压回主线程执行
```
一个请求在等待期间**不占用任何线程**，只占一份闭包内存——这就是单线程能扛几万并发连接的原因。

### 2. 事件循环六个阶段
| 阶段 | 干什么 |
| --- | --- |
| timers | 执行到期的 setTimeout / setInterval |
| pending callbacks | 上一轮遗留的系统回调（如 TCP 错误） |
| idle, prepare | 内部使用 |
| **poll** | 核心阶段：等 IO 事件并执行 IO 回调，大部分时间在这里 |
| check | 执行 setImmediate |
| close callbacks | 执行 `socket.on('close')` 等 |

每个阶段切换之间会清空微任务队列，优先级：`process.nextTick` > `Promise.then`。

记忆点：`setImmediate` 是「本轮 poll 之后」，`setTimeout(fn, 0)` 是「下一轮 timers」。所以拆分 CPU 任务、主动让出事件循环要用 `setImmediate`。

### 3. 三个致命短板与对策

**（1）CPU 密集任务卡死整个进程**
一段 200ms 的同步计算 = 这 200ms 内所有请求全部排队。
- `worker_threads` 把计算丢到工作线程（做成池复用，别每次 new）
- 大循环用 `setImmediate` 分片让出
- 极端场景交给 Rust / C++ addon，或独立的 Java / Go 服务

**（2）单进程吃不满多核**
- `cluster` / PM2 按核数起 N 个 worker，主进程 fork 后共享监听 fd
- 容器时代更推荐：**一个容器一个单进程 Node + K8s 多副本**，调度和扩缩容交给编排层
- 注意：worker 之间**内存不共享**，任何状态（session、计数器、本地缓存）必须外置到 Redis

**（3）一个未捕获异常拖垮所有在途请求**
- 每个 await 点该 try/catch，Promise 必须有 catch
- `unhandledRejection` / `uncaughtException` 只用来**记日志 + 优雅退出**，交给守护进程重启；不要带着脏状态硬撑
- 进程级兜底之外，所有下游调用**必须设超时**

### 4. 实战优化清单
- **别调同步 API**：`fs.readFileSync`、`crypto.pbkdf2Sync`、超大对象 `JSON.stringify`、回溯型正则（ReDoS）全都在阻塞事件循环
- **连接复用**：数据库用连接池；HTTP 客户端开 `keepAlive` 并调大 `maxSockets`，否则 TIME_WAIT 打满端口
- **流式 + 背压**：大文件 / 大响应走 `stream.pipeline`，靠 `highWaterMark` 反压，别整个读进内存
- **多级缓存**：进程内 LRU（抗热点、零网络开销）+ Redis（跨进程共享），配套处理穿透 / 击穿 / 雪崩
- **请求合并**：DataLoader 在同一 tick 内批量化，把 N 次查询压成一次 `IN`
- **限流 + 熔断 + 降级**：入口令牌桶限流，下游失败快速熔断，兜底返回缓存或默认值
- **监控事件循环延迟**：`perf_hooks.monitorEventLoopDelay()` 是 Node 服务最核心的健康指标，延迟上升就说明有人在阻塞主线程
- **内存**：堆有上限（`--max-old-space-size`），高并发下留意闭包 / 缓存导致的泄漏，用 heap snapshot 前后对比定位

## 二、Java 如何实现高并发

### 1. 四个演进阶段（回答主线）
| 阶段 | 模型 | 并发量级 | 代表 |
| --- | --- | --- | --- |
| BIO | 一连接一线程 | 几百~几千 | `ServerSocket`、老 Tomcat BIO |
| 线程池 + NIO | Reactor：少量 IO 线程 + 业务线程池 | 几万连接 | Netty、Tomcat NIO |
| 响应式 | 全异步 + 背压 | 几十万 | Spring WebFlux / Reactor |
| 虚拟线程 | 一任务一虚拟线程 | 百万级 | JDK 21 Loom、Spring Boot 3.2+ |

四个阶段的动机始终是同一个：**让「正在阻塞的请求」不再占着 OS 线程**。
- NIO 的答案：改成事件驱动 + 回调（性能好，代码难写）
- Loom 的答案：保留同步写法，运行时在阻塞点自动把虚拟线程从载体线程卸下（性能好，代码还简单）

### 2. NIO / Reactor 模型
```
Boss 线程（1 个）       accept 新连接，注册到 Worker
Worker 线程（N≈核数）   Selector 轮询就绪事件，做编解码
业务线程池              执行耗时逻辑，绝不在 Worker 线程里做阻塞操作
```
三件套：`Channel`（连接）、`Buffer`（数据）、`Selector`（多路复用，底层就是 epoll）。
Netty 在此之上补齐了：主从 Reactor、零拷贝（`CompositeByteBuf` / `FileRegion`）、池化 `ByteBuf`、EventLoop 与 Channel 绑定从而免掉大量线程安全问题。

> 一句话对比：Node 的事件循环 ≈ 单 Reactor 单线程；Netty 是主从 Reactor 多线程。**同一套思想，Java 做成了多核版本。**

### 3. 线程池：Java 高并发的地基
`ThreadPoolExecutor` 的执行顺序：
```
提交任务
 → 核心线程未满？   新建核心线程
 → 队列未满？       入队排队
 → 线程数 < max？   新建临时线程（空闲超 keepAliveTime 回收）
 → 都满了？         走拒绝策略
```
- **队列选择是最大的坑**：`LinkedBlockingQueue` 不传容量就是无界队列 = `maxPoolSize` 永远用不上 + 可能 OOM。生产环境一律用**有界队列**。
- **拒绝策略**：`AbortPolicy`（默认抛异常）、`CallerRunsPolicy`（调用方自己执行，天然反压，推荐）、`Discard*`（静默丢任务，慎用）。
- **别用 `Executors` 工厂方法**：`newFixedThreadPool` / `newSingleThreadExecutor` 是无界队列，`newCachedThreadPool` 线程数无上限。手写 `new ThreadPoolExecutor(...)`，并给线程起名方便排查。
- **线程数怎么定**：CPU 密集 `核数 + 1`；IO 密集 `核数 × (1 + 等待时间/计算时间)`，最终以压测为准。
- **按业务隔离线程池**（舱壁模式），避免一个慢下游把整个应用的线程耗光。

### 4. 并发工具箱（考点密集区）
| 需求 | 工具 | 关键点 |
| --- | --- | --- |
| 互斥 | `synchronized` / `ReentrantLock` | 锁升级：无锁→偏向→轻量级(CAS 自旋)→重量级；Lock 额外支持超时、可中断、公平锁、多条件队列 |
| 可见性 | `volatile` | 禁止重排 + 强制读写主存，**不保证原子性**；底层是 JMM 与 happens-before |
| 无锁计数 | `AtomicLong` / `LongAdder` | CAS 存在 ABA（用 `AtomicStampedReference`）；高竞争下 `LongAdder` 分段累加远快于 `AtomicLong` |
| 并发 Map | `ConcurrentHashMap` | JDK 8 起：CAS 插空桶 + `synchronized` 只锁单个桶；size 用 `CounterCell` 分段统计 |
| 读多写少 | `CopyOnWriteArrayList` | 写时复制，写贵、读完全无锁 |
| 线程隔离 | `ThreadLocal` | 线程池场景**必须 remove**，否则脏数据 + 内存泄漏（Entry 的 key 是弱引用，value 是强引用） |
| 线程协同 | `CountDownLatch` / `CyclicBarrier` / `Semaphore` | 都基于 **AQS**：`state` + CLH 队列 + CAS |
| 异步编排 | `CompletableFuture` | `thenCombine` 并行聚合、`allOf` 等全部完成；**务必传自定义线程池并设超时**，别用默认的 `ForkJoinPool.commonPool` |
| 极低延迟 | Disruptor | 环形数组 + 无锁 CAS + 缓存行填充解决伪共享 |

### 5. 虚拟线程（JDK 21，当下的标准答案）
- 用法：`Executors.newVirtualThreadPerTaskExecutor()`，Spring Boot 3.2+ 直接 `spring.threads.virtual.enabled=true`。
- 原理：虚拟线程挂在少量**载体线程**（ForkJoinPool）上运行，遇到阻塞 IO 就把栈拷到堆里、让出载体线程，IO 就绪再挂回来。**同步的写法，异步的性能。**
- 三条纪律：
  1. **不要池化**虚拟线程——创建成本极低，一任务一线程；
  2. 避开 **pinning**：在 `synchronized` 块里阻塞、或调用 native 方法会钉住载体线程，改用 `ReentrantLock`；
  3. 它只解决**阻塞等待**，不解决 CPU 密集——CPU 密集的上限仍由核数决定。
- 连带影响：按线程数做的限流、依赖 ThreadLocal 的对象池都要重新设计，限流改用 `Semaphore`。

## 三、架构层面（语言无关，真正决定量级）
单机调优最多榨出几倍，量级提升靠架构：

- **无状态 + 水平扩展**：状态外置到 Redis / DB，前面挂负载均衡，加机器就加吞吐
- **缓存分层**：浏览器 → CDN → 网关 → 本地缓存 → Redis → DB，命中率每提一点都是数量级收益
- **异步削峰**：非核心链路（发信、算分、写日志）丢 MQ，把「峰值 QPS」摊成「平均 QPS」
- **数据库是最终瓶颈**：慢查询与索引治理 → 读写分离 → 冷热分离 → 分库分表；连接池按 DB 承载力设，不是越大越好
- **稳定性三板斧**：限流（保护自己）、熔断（隔离故障下游）、降级（保住核心功能）；**所有远程调用必须有超时**
- **容量规划**：压测找到单机 QPS 与 RT 拐点，按 `并发数 = QPS × RT`（Little's 法则）推容量，留 30%~50% 余量

## 四、面试怎么答
被问「XX 如何实现高并发」，按这个顺序讲基本满分：

1. **模型**：Node 是单线程事件循环 + libuv 多路复用；Java 是线程池 + NIO/Reactor，JDK 21 之后是虚拟线程。
2. **为什么快**：两者本质在做同一件事——**让等待 IO 的请求不占用线程**。
3. **短板与规避**：Node 怕 CPU 密集、怕阻塞主线程（worker_threads / 多进程）；Java 怕线程膨胀、怕锁竞争（线程池隔离、无锁结构、虚拟线程）。
4. **通用手段**：缓存、异步、连接池、限流熔断、水平扩展。
5. **给数据**：讲清自己压测出的 QPS / P99 和优化前后对比，比背概念有说服力得多。

### 一句话总结
> **Node.js 用「一个线程调度成千上万个回调」实现高并发；Java 用「少量线程 + 多路复用」，并在 JDK 21 用虚拟线程合并两者的优点——同步的写法，事件驱动的性能。**
