# 浏览器的进程、线程与事件循环全景

结论先给：

- 一个 tab **不是一个进程**。它是「浏览器主进程 + 1~N 个渲染进程 + GPU / 网络 / 存储等服务进程」协作的结果。
- 渲染进程本身是**多线程**的，只有「渲染主线程上的 JS」是单线程。
- 事件循环**不属于 V8**。V8 只提供调用栈、堆和微任务队列；取宏任务、决定什么时候渲染，是渲染进程调度器（Blink Scheduler）干的事。
- 进程之间没有共享内存，只有 IPC。所以读 cookie、写 localStorage、发请求，本质都是**给别的进程发消息**。

---

## 一、进程全景

```
                        ┌────────────────────────────┐
                        │      Browser Process       │  全局唯一，不在沙箱里
                        │   UI Thread │ IO Thread    │
                        └──────────────┬─────────────┘
                                       │  Mojo IPC（唯一的通信方式）
   ┌────────────┬────────────┬─────────┴──┬────────────┬────────────┐
   ▼            ▼            ▼            ▼            ▼            ▼
┌────────┐  ┌────────┐  ┌────────┐   ┌────────┐   ┌────────┐  ┌────────┐
│Renderer│  │Renderer│  │  GPU   │   │Network │   │Storage │  │ Audio  │
│ a.com  │  │ b.com  │  │Process │   │Service │   │Service │  │Service │
└────────┘  └────────┘  └────────┘   └────────┘   └────────┘  └────────┘
  └── 沙箱 ──┘              └───── 这几个统称 Utility Process ─────┘
```

| 进程 | 数量 | 负责 | 崩掉的后果 |
| --- | --- | --- | --- |
| Browser | 1 | 标签页管理、地址栏、书签、权限、导航、sessionStorage 命名空间 | 整个浏览器退出 |
| Renderer | 每个 site 实例一个 | 解析 HTML/CSS、执行 JS、Layout/Paint、跑事件循环 | 只这一片页面变「Aw, Snap!」 |
| GPU | 1 | 栅格化结果合成、上屏 | 掉回软件合成，页面还活着 |
| Network Service | 1 | DNS、TLS、HTTP、HTTP Cache、**Cookie 的真身** | 请求全断，自动重启 |
| Storage Service | 1 | localStorage / IndexedDB / CacheStorage 落盘（LevelDB） | 存储 API 报错 |
| Audio / Video / 扩展 / ServiceWorker | N | 各自职责，扩展和 SW 本身也跑在渲染进程里 | 局部失效 |

两个容易被忽略的点：

- **除主进程外全部在沙箱内**，没有直接的文件和网络权限。渲染进程里的内存漏洞打不穿系统，这是多进程架构最主要的收益。
- **进程数不是无上限的**。内存吃紧时 Chrome 会合并渲染进程（`--renderer-process-limit`），低配机器上不同站点的 tab 可能挤在同一个渲染进程里，此时「一个 tab 卡死不影响别人」就不成立了。

## 二、一个 tab 到底占几个进程

以「`a.com` 的页面里嵌了一个 `b.com` 的 iframe」为例：

```
 一个 tab 里的 frame tree                 承载它的进程
 ────────────────────────────────────────────────────────────────
 tab (WebContents)                     →  Browser Process
  └─ 主 frame  https://a.com           →  Renderer #1  site = a.com
      ├─ iframe  https://x.a.com       →  Renderer #1  同 site，复用
      └─ iframe  https://b.com         →  Renderer #2  跨 site，OOPIF
 所有 frame 共用                        →  GPU / Network / Storage Service
```

Site Isolation 的规则（Chrome 默认开启）：

- 分进程的粒度是 **site**（scheme + eTLD+1），不是 origin。`a.com` 与 `x.a.com` 同 site、同进程；`a.com` 与 `b.com` 不同 site、拆进程。
- 跨站 iframe 会变成 **OOPIF**（Out-of-Process iframe），单独一个渲染进程。所以「一个 tab N 个渲染进程」是常态，不是异常。
- 同 site 且互相有脚本引用关系的页面（`window.open` 出来的、同一个 browsing context group），会**复用同一个渲染进程** —— 其中一个页面跑死循环，另一个也会一起卡住。
- 这么设计的动机是 Spectre 类侧信道：同一进程的地址空间可以被间接读出，所以**只有进程边界才是可靠的安全边界**。

亲眼验证：`chrome://process-internals/#web-contents` 看 frame tree 到进程的映射，或 `Shift+Esc` 打开任务管理器，跨站 iframe 会作为独立条目出现。

## 三、渲染进程内部：它是多线程的

```
┌─ Renderer Process（一个 site 实例，跑在沙箱里）
│
├─ Main Thread　渲染主线程 ← 全部拥堵都发生在这条线上
│   ├─ V8 Isolate：Call Stack + Heap + 微任务队列
│   ├─ Blink：HTML/CSS 解析 → DOM/CSSOM → Style → Layout → Paint
│   └─ Scheduler：多条带优先级的任务队列（事件循环的实现体）
│
├─ Compositor Thread　合成线程
│   └─ 已提交图层的滚动 / transform / opacity 动画，向 GPU 提 tile
│
├─ Raster / Tile Worker Threads　栅格线程池
│   └─ 把 paint 指令变成位图
│
├─ Web Worker Threads　每条一个独立 V8 Isolate + 独立事件循环
│
└─ IO Thread　只收发 Mojo IPC，不跑业务代码
```

| 线程 | 跑什么 | 主线程长任务会拖累它吗 |
| --- | --- | --- |
| 主线程 | 解析、Style、Layout、Paint、JS、事件回调 | 它就是被拖累的那个 |
| 合成线程 | 图层滚动与合成动画 | 不会。主线程卡死时**页面还能滚**，但滚出来的是旧位图 |
| 栅格线程池 | 位图生成 | 不会 |
| Worker | Worker 里的 JS | 不会 |
| IO 线程 | IPC | 不会 |

由此得到两个可以直接用在优化里的推论：

- `transform` / `opacity` 动画可以完全交给合成线程，即使主线程在忙也能保持 60fps；改 `width` / `top` / `left` 必须回主线程做 Layout，主线程一忙就掉帧。
- 「主线程卡住但滚动还有反应、内容却不更新」这种现象，就是合成线程还活着、主线程没法提交新帧。

## 四、JS 单线程与事件循环的关系

先把三层分清，很多混乱都来自把它们混成一坨：

| 层 | 是谁 | 提供什么 |
| --- | --- | --- |
| V8 Isolate | JS 引擎实例 | Call Stack、Heap、**微任务队列**。只会「执行到栈空」，不知道事件循环存在 |
| Blink Scheduler | 渲染进程主线程的调度器 | 多条**宏任务队列** + 优先级 + 决定何时渲染。事件循环的真身 |
| 规范里的 event loop | 抽象模型 | 一个 agent（主线程、每个 Worker）一个 event loop |

```
 ┌── 生产者：别的线程 / 别的进程 ──────────────────
 │   Network Service    响应到达、fetch resolve
 │   Browser Process    用户 click / keydown / 导航
 │   Scheduler 延时队列  setTimeout / setInterval 到期
 │   Compositor         vsync 信号、scroll
 └───────────────┬────────────────────────────────
                 │ postTask 跨线程投递（唯一需要加锁的地方）
                 ▼
╔═ 渲染主线程 Main Thread ════════════════════════════════════════
║
║ 【宏任务队列】按任务源分成多条，按优先级挑一条非空的
║   ├─ user-interaction   click / keydown       ← 优先级最高
║   ├─ networking         xhr.onload / fetch 回调
║   ├─ timer              setTimeout / setInterval
║   └─ DOM manipulation / history / idle ...
║         │
║         │ 每一轮只取 1 个宏任务，交给 V8 执行
║         ▼
║ ┌─ V8 Isolate（「JS 单线程」的物理载体）
║ │   Call Stack     同步代码压栈 / 出栈，栈空才算这个宏任务结束
║ │   Heap           对象、闭包、DOM 的 JS 包装对象
║ │   Microtask Q    Promise.then / queueMicrotask / await 后续代码
║ └──────────────────────────────────
║         │
║         │ 栈空 → 清空整个微任务队列
║         │        （清空过程中新入队的也要清完 → 能饿死渲染）
║         ▼
║     到 vsync 了吗？ ── 没到 ──→ 回去取下一个宏任务
║         │ 到了（约 16.7ms 一次）
║         ▼
║ 【渲染步骤】rAF 回调 → ResizeObserver → IntersectionObserver
║             → Style → Layout → Paint → commit 给合成线程
║         │
║         ▼ 这一帧还有剩余时间？ → requestIdleCallback
╚════════════════════════════════════════════════════════════════
```

需要记住的只有三条：

1. **一轮只取一个宏任务**。「宏任务队列」是复数，浏览器按任务源分队列并带优先级，所以 `click` 回调可以插到一堆 `setTimeout` 前面 —— 这也是浏览器和 Node 六阶段固定轮转的最大区别。
2. **每次调用栈清空就清空整个微任务队列**，包括清空过程中新入队的微任务。所以 `Promise.then` 里递归地再产生微任务，可以让渲染永远排不上队（页面假死但 CPU 满载）。
3. **渲染不是每轮都做**，它只在 vsync 附近做一次，顺序固定：`rAF → ResizeObserver → IntersectionObserver → Style → Layout → Paint → commit`。

为什么 JS 必须单线程：**因为它能改 DOM**。两条线程同时改一棵 DOM 树就必须给节点加锁，在 DOM 这种复杂度下必然走向死锁和不可预测的重排。Web 选了「单线程 + 队列」这条心智负担最低的路，代价就是一个长任务能冻结整个页面。所以后来加线程的方案（Web Worker）一律**不给 DOM 访问权**。

## 五、一帧里到底发生了什么

```
 时间 →    |<--------------- 16.7ms 一帧 -------------->|
           |                                            |
 正常:     [JS][u][JS][u]...[rAF][Style|Layout|Paint]....[idle]
           ^vsync                                       ^vsync 按时出帧
                                    ↑ commit 给合成线程 → GPU 上屏

 长任务:   [================= JS 120ms ==========================>
           ^vsync     ^vsync     ^vsync     ^vsync     ^vsync
           └── 这 5 次 vsync 一次渲染步骤都没执行 → 连续掉帧、点击无响应

 说明：[JS] = 一个宏任务，[u] = 那一轮的微任务清空
```

- **长任务**的定义就是：主线程上单个任务执行超过 50ms。TBT / INP 量的正是「宏任务把渲染挤到了什么程度」。
- 拆长任务的手段：`await scheduler.yield()`、`scheduler.postTask()` 指定优先级、退化方案 `setTimeout(fn, 0)`，或整块搬去 Worker。
- 后台 tab 会被节流：`setTimeout` 最小间隔被拉到 1s 以上，`rAF` 直接不执行（页面不可见就没有 vsync 驱动的渲染步骤）—— 所以计时器逻辑不能依赖 `setInterval` 累计时间，要用 `Date.now()` 校准。

## 六、存储归属：每种存储真正住在哪个进程

```
JS 代码（渲染进程 · 主线程）
  │
  ├─ 变量 / 闭包 / DOM 节点 ───→ 就在本进程：V8 Heap + Blink 内存
  │                              进程一挂全部丢失
  │
  ├─ document.cookie ──────IPC──→ Network Service
  │                              HttpOnly 的那部分会被过滤，渲染进程根本看不到
  │
  ├─ localStorage.getItem ─同步IPC→ Storage Service ──→ LevelDB 落盘
  │                              ⚠ 同步：主线程真的停下来等回消息
  │
  ├─ sessionStorage ───────IPC──→ Browser Process 里的 session 命名空间
  │                              按「顶层 tab」隔离
  │
  ├─ indexedDB / caches ───异步IPC→ Storage Service
  │
  └─ fetch / xhr ──────────IPC──→ Network Service ──→ HTTP Cache / 网络
```

| 存储 | 归属进程 | 隔离维度 | 同步性 | 容量 | 生命周期 |
| --- | --- | --- | --- | --- | --- |
| JS 变量 / DOM | 渲染进程 | 该 frame | 同步 | 堆上限（64 位约 4GB，实际 2~4GB） | 进程存活期 |
| Cookie | Network Service | domain + path | `document.cookie` 同步 | 4KB/条 | Expires / 会话 |
| localStorage | Storage Service | origin（+ 顶层站点分区） | **同步阻塞** | 约 5~10MB | 永久，手动清 |
| sessionStorage | Browser Process | origin × 顶层 tab | **同步阻塞** | 约 5~10MB | 关 tab 即失效 |
| IndexedDB | Storage Service | origin（+ 分区） | 异步 | 磁盘配额的一部分 | 永久 |
| CacheStorage | Storage Service | origin | 异步 | 同上 | 永久 |
| HTTP Cache | Network Service | 按 network isolation key 分区 | 对 JS 不可见 | 由浏览器管理 | 由响应头决定 |

面试里能加分的几点：

- **localStorage 是性能红线**：同步 API + 跨进程 IPC，循环里读写就是在主线程上串行等 IPC，是很典型的卡顿源。要频繁读就在启动时一次性读进内存。
- **sessionStorage 隔离到 tab**，不是隔离到 origin：新开一个同源 tab 拿不到；「复制标签页」会复制一份快照出来，此后两边各自独立。
- **HttpOnly cookie 在渲染进程里拿不到**，因为它只存在 Network Service —— XSS 偷不走 token 靠的就是这条进程边界，不是 JS 层的约定。
- **第三方存储分区**（Storage Partitioning / CHIPS）：`b.com` 嵌在 `a.com` 里时，它的 localStorage / IndexedDB 的 key 是 `(b.com, 顶层=a.com)`，和 `b.com` 作为顶层页面打开时**不是同一份数据**。
- 只有渲染进程内存里的东西会随进程消失，所以 tab 被 discard 或崩溃后恢复现场，只能靠 sessionStorage 这类由**别的进程**持有的存储。

## 七、Worker：第二条真正的 JS 线程

```
 ┌─ 渲染主线程 · V8 Isolate #1
 │    Call Stack / Heap / Microtask Queue / Task Queues
 │    ✔ DOM、window、localStorage
 └───────────────┬─────────────
                 │  postMessage：结构化克隆 = 拷贝一份，不共享
                 │  Transferable（ArrayBuffer / ImageBitmap）= 转移所有权
                 │  SharedArrayBuffer = 唯一真正共享的内存
 ┌───────────────┴─────────────
 │  Worker 线程 · V8 Isolate #2
 │    Call Stack / Heap / Microtask Queue / Task Queues（各自一套）
 │    ✘ 没有 DOM、没有 window；有 self、fetch、IndexedDB、WASM
 └─────────────────────────────
```

- 「JS 是单线程」准确的说法是：**每个 agent 一个线程、一个事件循环**。开 Worker 是加了一个新 agent，不是把主线程变成多线程。
- 结构化克隆是**同步发生在发送方主线程上**的：传一个几十 MB 的对象，`postMessage` 本身就成了新的长任务 —— 所以大数据一定要用 `Transferable` 转移所有权。
- 适合搬去 Worker 的活：解析大 JSON、加解密、图像处理、大列表 diff、埋点聚合。
- ServiceWorker 是另一码事：它跑在**自己的渲染进程**里，没有页面、生命周期独立，负责拦网络请求。

## 八、面试追问速答

| 问题 | 答法 |
| --- | --- |
| 一个 tab 是一个进程吗 | 不是。至少涉及主进程 + 渲染进程 + GPU/网络/存储，跨站 iframe 还会再拆渲染进程 |
| 为什么 JS 要单线程 | 它能改 DOM；多线程改 DOM 必须加锁，DOM 复杂度下必然死锁 |
| GUI 渲染和 JS 互斥吗 | 说「互斥」不准确 —— 它们在同一条主线程上**排队**，不存在两者并行的可能 |
| 一个 tab 崩了为什么别的还活着 | 渲染进程隔离；但同 site 且有脚本关联的页面会共用进程，会一起卡 |
| 为什么跨源 iframe 也要单独进程 | Spectre 侧信道，进程边界才是安全边界（Site Isolation / OOPIF） |
| 长任务为什么掉帧 | vsync 到了主线程还在跑那个宏任务，渲染步骤排不上 |
| rAF 比 setTimeout 稳在哪 | rAF 挂在渲染步骤之前、与 vsync 天然对齐；setTimeout 只是延时任务，会被长任务推迟、后台还会被节流到 ≥1s |
| 微任务能饿死什么 | 能饿死宏任务和渲染 —— 微任务队列要清空才继续，递归产生微任务就永远清不完 |
| Node 的事件循环差别 | Node 是 libuv 的六个固定阶段轮转 + 线程池，浏览器是多条带优先级的任务队列 + vsync 驱动的渲染步骤，细节见 [高并发.md](高并发.md) |

## 怎么亲眼看到这些

- `Shift+Esc` 任务管理器：逐进程的内存 / CPU，跨站 iframe 会单独成行。
- `chrome://process-internals/#web-contents`：frame tree 到进程的映射。
- Performance 面板：Main、Compositor、Raster 是分开的轨道；长任务带红色三角；Frames 轨道能看到掉帧。
- `new PerformanceObserver(...).observe({type:'longtask'})`：线上采集长任务。
- `chrome://tracing`：能看到 vsync、commit、栅格化的完整时间线。

调试手法见 [浏览器调试.md](../浏览器/浏览器调试.md)，渲染流水线细节见 [浏览器.md](../浏览器/浏览器.md)。
