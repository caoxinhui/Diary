# react-imvc 原理

IMVC = **I**somorphic **M**odel **V**iew **C**ontroller。它要解决的不是「React 怎么写」，而是**同构**：同一份业务代码，在 Node 端跑一次产出首屏 HTML，在浏览器端再跑一次接管交互。

Next.js 的思路是「页面组件 + 若干约定好的静态方法」，imvc 的思路是**把一个页面的全部逻辑收进一个 Controller 类**，用生命周期钩子区分服务端 / 客户端。理解 imvc 只需要抓住一句话：

> **Controller 是一个能在 Node 和浏览器里各跑一遍的类；它的 `init()` 返回一个 React 元素，谁调用它就由谁负责渲染。**

---

## 一、四个包的分工

react-imvc 本身很薄，真正的同构引擎在 `create-app` 里。

```
┌─ react-imvc ────── 约定层
│    Controller 基类、生命周期、fetch/preload、Link/Input 等组件
│    express server、webpack 配置、目录约定（src/routes）
│
├─ create-app ────── 同构引擎（同一套 API，client / server 两个入口）
│    matcher    : url  → { controller, params, pattern }
│    loader     : 路由模块 → Controller 构造函数（支持异步 import）
│    viewEngine : element → 渲染（client: ReactDOM，server: renderToString）
│    controller 缓存池（KeepAlive 的实现处）
│
├─ create-history ── history 的一个 fork
│    多了 listenBefore / listenBeforeUnload，location 上多了 raw
│
└─ relite ────────── 一个极简 store，action 本身就是 reducer
```

对应版本：`packages/react-imvc-v3/package.json` 里 `react-imvc@3.5.5`，依赖 `relite ^3.0.7`、`create-app ^2.1.0`、`create-history ^2.1.1`。master 已经是 monorepo，v3 源码在 `packages/react-imvc-v3/src`，v2 在 `packages/react-imvc-v2`。

三层的关系可以这样记：

| 层 | 谁调用谁 |
| --- | --- |
| react-imvc | 提供 `Controller` 基类 + express 中间件，把配置塞给 create-app |
| create-app | 拿到 url → 找到 Controller → `new` 出来 → 调 `init()` → 把返回值交给 viewEngine |
| Controller | 自己准备好 store 和数据，返回 `<ViewManager controller={this} />` |

### create-app 的三个注入点

create-app 自己**什么都不做**，三件事全靠外部注入，这是它能同时服务两端的原因：

```ts
// 默认实现全是「哑」的（create-app/src/share/defaultSettings.ts 等）
loader:     (value) => value              // 恒等函数
viewEngine: { render(html, ctrl, container) { container.innerHTML = html } }  // client 默认
viewEngine: { render(html) { return String(html) } }                          // server 默认
```

react-imvc 把这三处换成 React 版本：`webpackLoader` / `commonjsLoader` 负责 `import()` 与 `.default` 解包，viewEngine 换成 `ReactDOM.hydrate/render` 和 `renderToNodeStream/renderToString`。

`matcher` 用的是 **path-to-regexp v1**，`createMatcher` 在启动时把每条路由预编译成正则，匹配时**线性扫描、第一个命中即返回**：

```ts
for (let i = 0; i < routeLength; i++) {
  let route = finalRoutes[i]
  let strMatches = route.regexp.exec(finalPathname)
  if (!strMatches) continue
  return { path: route.path, params: getParams(strMatches, route.keys), controller: route.controller }
}
return null    // 未命中 → 抛 ReqError(404)
```

所以 imvc **没有嵌套路由、没有优先级排序**，路由顺序就是匹配顺序，`/user/:id` 写在 `/user/new` 前面会把后者吃掉。

两端 API 也不一样：

| | `create-app/client` | `create-app/server` |
| --- | --- | --- |
| 暴露的方法 | `{ start, stop, render, history, subscribe }` | `{ render, history }` |
| history | 浏览器 history + `useBeforeUnload(useQueries(useBasename(...)))` | `createMemoryHistory` + `useQueries(useBasename(...))` |
| 生命周期 | `history.listen` 驱动反复 render，带 controller 缓存池 | 一次性 `render(url, context)` → `{ content, controller }` |
| 容器 | `document.querySelector(settings.container)` | 无

## 二、SSR：一个请求的完整链路

```
浏览器请求 /detail/123
   │
   ▼
express（src/entry/server.ts：helmet / compression / cookieParser / static ...）
   │  中间件里准备好 res.locals.assets、basename、publicPath、appSettings
   ▼
createPageRouter 的 router.all('*')      ← src/page/createPageRouter.tsx
   │  组装 context = { req, res, basename, publicPath, serverPublicPath,
   │                   restapi, assets, preload:{}, isServer:true, isClient:false }
   ▼
app.render(req.url, context)             ← create-app/server
   │  ① matcher(pathname) → { controller, params, pattern }
   │  ② loader(controller) → Controller 构造函数（支持 () => import()）
   │  ③ wrapController：注入 location / context / matcher / loader / routes
   │  ④ new Ctrl(location, context)
   │  ⑤ await controller.init()          ← 业务逻辑全在这一步
   │  ⑥ viewEngine.render(element)       ← renderToNodeStream（默认）/ renderToString
   ▼
{ content, controller }
   │  initialState = controller.store.getState()
   │  htmlConfigs  = initialState.html   → <title> / description / keywords
   │  controller.destroy()
   ▼
renderToStaticMarkup(<LayoutView {...res.locals} content initialState />)
   │  LayoutView 里注入三个全局变量（src/page/view.tsx）
   ▼
res.end('<!DOCTYPE html>' + html)
```

注入客户端的那段脚本就是同构的接头：

```tsx
// packages/react-imvc-v3/src/page/view.tsx
<Script>{`
  (function() {
      window.__INITIAL_STATE__ = ${JSON.stringify(props.initialState)}
      window.__APP_SETTINGS__ = ${JSON.stringify(props.appSettings)}
      window.__PUBLIC_PATH__ = '${props.publicPath}'
  })()`}</Script>
```

几个容易被问到的细节：

- **`renderMode`** 决定用 `renderToNodeStream` 还是 `renderToString`，默认前者。注意它**并没有真的流式响应**：`renderToNodeStream` 的输出会被 `on('data')` 收集成一个完整 Buffer，再作为字符串塞进 LayoutView。所以选它只是绕开了 `renderToString` 的单次大字符串拼接，首字节时间并不会变快。
- **`content` 为空就直接 `return`**，不渲染布局 —— 说明 Controller 已经通过 `context.res` 自己重定向或响应了。⚠️ 反过来说，Controller 既不返回内容也不重定向，这个请求就**永远挂着**，直到客户端超时。
- Controller 会**劫持 `React.createElement`**（做错误边界），所以服务端在流结束 / `finally` 里必须把它还原，否则会污染下一个请求。
- `config.SSR === false` 时前置中间件直接 `res.render(layoutView)`，不注入 `__INITIAL_STATE__`，退化成纯 CSR。
- **404 是怎么走出来的**：`matcher` 没匹配上 → create-app 服务端的 `fetchController` reject 一个 `ReqError(..., 404)` → `router` 的 `catch` 把它交给 `next(error)` → `devErrorHandler` / `prodErrorHandler` 按 `err.status` 出页面。`start/index.ts` 里注册的那个 `catch404` 实际上**永远走不到**，因为 `router.all('*')` 一定先匹配成功。

## 三、客户端接管与单页跳转

客户端入口做的事很少（`src/entry/client.ts`）：读全局变量、把服务端注入的 CSS 收回来、创建 app、开始监听 history。

```ts
// src/entry/client.ts（v3）
__webpack_public_path__ = window.__PUBLIC_PATH__ + '/'
let shouldHydrate = !!window.__INITIAL_STATE__        // 有 SSR 状态才 hydrate

const viewEngine = { render(view, controller, container) {
    if (shouldHydrate) { shouldHydrate = false; ReactDOM.hydrate(view, container) }
    else { ReactDOM.render(view, container) }
} }

const app = createApp({ ...appSettings, loader: webpackLoader, routes, viewEngine })
app.start()
```

`app.start()` 之后每一次 url 变化都走同一条路径，**缓存命中与否决定走 `restore` 还是 `init`**：

```
history 变化（Link 点击 / history.push / 前进后退）
   │
   ▼
destroyController()                    上一个 controller：
   │                                     KeepAlive=false → 移出缓存池并 destroy()
   │                                     KeepAlive=true  → 留在池子里
   ▼
getControllerFromCache(location)       缓存 key = location.raw
   │
   ├── 命中 ──→ controller.restore(location, context)
   │              dispatch __PAGE_DID_BACK__ → pageDidBack() → bindStoreWithView()
   │              状态、DOM 都还在，直接复用
   │
   └── 未命中 → loader 加载模块 → new Ctrl → controller.init()
   │
   ▼
renderToContainer(element) → saveControllerToCache(controller)
   ▼
viewEngine.render → 首次是 ReactDOM.hydrate，之后都是 ReactDOM.render
```

- `location.raw` **不是 history 的概念，是 create-app 加上去的**：`raw = location.pathname + location.search`（已去掉 basename，**不含 hash**）。它是整个框架里的「页面身份」—— controller 缓存的 key、`ViewManager` 里 view map 的 key 和 React `key`、`reload()` 的目标，全用它。所以**同一个路由带不同 query 算两个页面**，而只有 hash 不同则算同一个页面。
- 同时挂上去的还有 `pattern`（命中的路由模式，如 `/user/:id`）和 `params`（路径参数）。
- 缓存池由 `create-app` 的 `createCache(cacheAmount)` 实现，**默认只存 10 个**，超了淘汰最早的 key。
- `reload()` 内部会先 `removeFromCache()` 再走一遍，否则会命中缓存变成 `restore`。

## 四、Controller.init() 的执行顺序（最核心的一段）

`init()` 只是包了一层错误处理，真正的顺序在 `initialize()` 里（`src/controller/index.tsx`）。它有**三条分支**，分清这三条，生命周期就不会记乱：

```
                       new Controller(location, context)
                                  │
                     ┌────────────┴────────────┐
                  服务端                     客户端
                     │                          │
          SSR === false ?                有 __INITIAL_STATE__ ?
          │           │                   │              │
         是          否                  有（首屏 hydrate）  没有（单页跳转）
          │           │                   │              │
   flushHeaders   ┌───┴──────────────┬─────┘              │
   返回 <Loading> │                  │                    │
   （交给客户端）  ▼                  ▼                    ▼
        ┌─────────────────── 公共部分 ────────────────────────┐
        │ ① 绑定 this.fetch / this.prefetch                   │
        │ ② Model 拆成 { initialState, ...actions }           │
        │ ③ deepCloneInitialState（默认 true，防跨请求污染）    │
        │ ④ finalInitialState = { ...initialState,            │
        │      ...__INITIAL_STATE__, ...baseState }           │
        │    baseState = { location, basename, publicPath,    │
        │                  restapi }                          │
        │ ⑤ 没有 SSR 状态 → await getInitialState(state)       │
        │    有   SSR 状态 → stateDidReuse(state)              │
        │ ⑥ await getFinalActions({ ...内置actions, ...你的 }) │
        │ ⑦ store = createStore(finalActions, finalInitialState)│
        └───────────────────────┬─────────────────────────────┘
                    ┌───────────┴────────────┐
              hydrate 分支                 全新渲染分支
                    │                          │
          bindStoreWithView()        await shouldComponentCreate()
          缺失的 preload 才补拉         └ 返回 false → 什么都不渲染（常用于跳转）
          await viewWillHydrate()             │
                    │                 Promise.all([
                    │                   componentWillCreate(),
                    │                   fetchPreload()          ← 二者并行
                    │                 ])
                    │                 flushHeaders()  ← Early Hints
                    │                 bindStoreWithView()（服务端是空操作）
                    └───────────┬──────────────┘
                                ▼
                    return <ViewManager controller={this} />
                                │  客户端挂载后，由 ControllerProxy 触发：
                                ▼
                    componentDidFirstMount → componentDidMount
```

全部钩子（都是可选的，不写就不调）：

| 钩子 | 时机 | 环境 |
| --- | --- | --- |
| `getInitialState(state)` | 建 store 之前，可以 `await` 拉首屏数据 | 服务端 + 客户端跳转，**hydrate 时跳过** |
| `getFinalActions(actions)` | 拿到合并后的 actions，可再包一层 | 两端 |
| `shouldComponentCreate()` | 首次渲染前，返回 `false` 则不渲染 | 两端（hydrate 跳过） |
| `componentWillCreate()` | 首次渲染前，与 `fetchPreload` 并行 | 两端（hydrate 跳过） |
| `stateDidReuse(state)` | 复用了 `__INITIAL_STATE__` | 仅客户端 |
| `viewWillHydrate()` | hydrate 之前最后一步 | 仅客户端 |
| `componentDidFirstMount()` | 该 controller 第一次挂载 | 仅客户端 |
| `componentDidMount()` | 每次挂载（含 `restore` 回来） | 仅客户端 |
| `stateDidChange(data)` | 每次视图刷新后，`data` 带 actionType / 前后 state | 仅客户端 |
| `pageWillLeave(location)` | 离开页面前（`history.listenBefore`） | 仅客户端 |
| `componentWillUnmount()` | 卸载 | 仅客户端 |
| `pageDidBack(location)` | 缓存命中被 `restore` 时 | 仅客户端 |
| `windowWillUnload()` | 关闭 / 刷新浏览器 | 仅客户端 |
| `errorDidCatch(err, type)` | `type` 为 `controller` / `model` / `view` | 两端 |
| `getViewFallback()` / `getComponentFallback()` | 出错时的兜底 UI | 两端 |
| `handleInputChange(path, value, oldValue)` | `<Input>` 变更时的拦截点，默认原样返回 | 仅客户端 |

客户端的 mount 类钩子都不在 Controller 里触发，而是靠一个**渲染 null 的哨兵组件** `ControllerProxy`：

```tsx
// src/component/ControllerProxy.ts（v3）
componentDidMount() {
  this.updateDocumentTitle()                   // state.html.title → document.title
  if (!controller.meta.hadMounted) {
    controller.meta.hadMounted = true
    this.emit('componentDidFirstMount')
  }
  this.emit('componentDidMount')
}
componentWillUnmount() { this.emit('componentWillUnmount') }
render() { return null }
```

四个必须记住的结论：

- **`getInitialState` 在 hydrate 时不执行**。首屏数据只在服务端取一次，随 HTML 带下来；所以里面不能碰 `window` / `localStorage`。
- **服务端不会触发任何 `componentDidXxx`**，SSR 想要的数据必须在 `getInitialState` / `componentWillCreate` 里拿。
- `shouldComponentCreate()` 返回 `false` 是拦截页面的正规姿势（鉴权失败 → `redirect` → 返回 false）。
- `deepCloneInitialState` 默认 `true`：Node 端模块是单例，`initialState` 是同一个对象引用，不深拷贝会**跨请求串数据**。

`meta` 上挂的是这个 controller 实例的运行时状态：`{ id, viewId, key, isDestroyed, hadMounted, unsubscribeList, isInitializing }`。注意 `location.key` 被特意搬到了 `meta.key` —— 因为它每次都变，留在 `location` 里会让 SSR 的 `initialState` 字节不稳定，破坏 Etag / 304。

## 五、Model：relite 是怎么比 redux 薄的

relite 里**没有 reducer 的概念，action 本身就是 reducer**：`(state, payload) => newState`。`createStore` 把它们 curry 成可直接调用的形式：

```js
// relite/index.js
var curryActions = getKeys(actions).reduce(function (obj, actionType) {
    if (typeof actions[actionType] === 'function') {
        obj[actionType] = function () { return dispatch(actionType, ...arguments) }
    } else throw new Error('Action must be a function')
    return obj
}, {})
```

所以业务里是 `actions.UPDATE_USER({ name })`，不需要 `dispatch({ type, payload })`，也不需要 switch。其余语义：

- `dispatch` 内部调 `actions[type](currentState, payload)`，**只有 `nextState !== currentState` 才 `replaceState` 并 `publish`** —— 返回原对象等于不更新。
- 在 reducer 里再 dispatch 会直接抛错。
- store 暴露 `{ actions, getState, replaceState, dispatch, subscribe, publish }`。
- **没有异步 action**：relite 3.0.0 把 action 允许返回 `Promise | Function` 的类型定义删掉了，action 只能是同步纯函数。所以 imvc 里异步逻辑一律写在 Controller 的方法里（`await this.fetch(...)` 后再 `this.store.actions.UPDATE_STATE(...)`），不需要 thunk / saga 这类中间件 —— Controller 就是那一层。

内置的公共 actions（`src/controller/actions.ts`）：

| action | 作用 |
| --- | --- |
| `UPDATE_STATE` | 浅合并，最常用 |
| `UPDATE_STATE_BY_PATH` | 按 `a.b.c` 路径改值 |
| `UPDATE_INPUT_VALUE` | 就是 `UPDATE_STATE_BY_PATH` 的别名，给 `<Input>` 用 |
| `__PAGE_DID_BACK__` | `restore` 时把新 location 写回 state |
| `INDENTITY` | 什么都不做，用来触发一次刷新 |

v3 的合并顺序是 `getFinalActions({ ...shareActions, ...actions })` —— **你的同名 action 会覆盖内置的**；v1/v2 是反过来的 `{ ...actions, ...shareActions }`，内置的赢。升级时这是个坑。

### store 到 view 的绑定

```js
// bindStoreWithView（v2 源码，v3 逻辑相同、多了防抖控制）
if (store) {
  let unsubscribe = store.subscribe(data => {
    this.refreshView()
    if (this.stateDidChange) this.stateDidChange(data)
  })
  meta.unsubscribeList.push(unsubscribe)
}
```

v3 在这里包了一层 `_.debounce(fn, 5)`，并用 `disableBatchRefresh`（**默认 `true`**）决定要不要立刻 `flush`：

- 默认行为 = 每次 state 变化同步刷新，行为直观；
- 设成 `false` 才启用 5ms 合并，适合一次交互里连续 dispatch 很多次的场景；
- 需要在批量中强制同步渲染时用 `this.flushSync(fn)`。

`refreshView` 本身由 create-app 的客户端包装类注入：`refreshView(view = this.render()) { renderToContainer(view, this) }` —— 也就是说 `ctrl.refreshView(<div>test</div>)` 可以直接把任意元素塞到容器里，调试很方便。

### 怎么接上 redux devtools

relite 不是 redux，但可以做一层双向桥：relite 的每次 `publish` 转成 redux 的 `dispatch`，devtools 里回放（时间旅行）时再 `replaceState` 回 relite。`isSync` 这个标志位是为了避免两边互相触发形成死循环。

```js
let reduxStore = __REDUX_DEVTOOLS_EXTENSION__(store.getState, store.getState(), options)
let isSync = false

store.subscribe(data => {
  if (!data || data.actionType === __FROM_REDUX_DEVTOOLS_EXTENSION__) return
  isSync = true
  reduxStore.dispatch({ type: data.actionType, payload: data.actionPayload })
  isSync = false
})

reduxStore.subscribe(() => {
  if (!isSync) {
    store.replaceState(reduxStore.getState(), {
      actionType: __FROM_REDUX_DEVTOOLS_EXTENSION__,
      previousState: store.getState(),
      currentState: reduxStore.getState()
    })
  }
})
```

## 六、View 与 KeepAlive：多个页面同时在 DOM 里

单页跳转时，imvc **不卸载旧页面**，而是让所有缓存过的页面都留在 DOM 上，用 `display:none` 控制可见性 —— 这样返回时 DOM、滚动位置、输入框内容全都还在。

```
ViewManager
 ├─ views:     { '/list': <View/>, '/detail/1': <View/> }   按 location.raw 存元素
 ├─ scrollMap: { '/list': 320 }                             离开时记下 window.scrollY
 └─ render():
      Object.keys(views).map(path =>
        <ViewItem isActive={path === controller.location.raw} ... />)
      + <ControllerProxy controller={controller} />

ViewItem.shouldComponentUpdate(next):
   next.isActive ? (显示 + window.scroll(0, scrollY)) : (container.style.display = 'none')
   return next.isActive        ← 非激活的 ViewItem 直接不再渲染
```

完整实现（v2 源码，`src/component/ViewManager.js`）：

```jsx
export default class ViewManager extends React.Component {
	static ignoreErrors = true
	views = {}
	scrollMap = {}
	constructor(props, context) {
		super(props, context)
		this.addItemIfNeed(props.controller.location.raw)
	}
	addItemIfNeed(key) {
		if (!this.views.hasOwnProperty(key)) {
			this.views[key] = null
		}
	}
	// 缓存池里已经没有的页面，把 view 和滚动位置一起清掉
	clearItemIfNeed() {
		let { views, scrollMap } = this
		let cache = this.props.controller.getAllCache()

		for (let key in views) {
			if (!cache.hasOwnProperty(key)) delete views[key]
		}
		for (let key in scrollMap) {
			if (!cache.hasOwnProperty(key)) delete scrollMap[key]
		}
	}
	componentWillReceiveProps(nextProps) {
		let currentPath = this.props.controller.location.raw
		let nextPath = nextProps.controller.location.raw
		// 路由变了，先记住当前页面的滚动位置
		if (currentPath !== nextPath) {
			this.scrollMap[currentPath] = window.scrollY
		}
		this.addItemIfNeed(nextPath)
		this.clearItemIfNeed()
	}
	renderView(path) {
		let { controller } = this.props
		let currentPath = controller.location.raw

		// 不是当前页面 → 复用上次渲染好的元素，不重新求值
		if (currentPath !== path) {
			return this.views[path]
		}

		let { meta, store, handlers, View } = controller
		let state = store.getState()
		let actions = store.actions

		// View 是业务自己写的组件，imvc 给它注入 state / handlers / actions
		let view = (
			<GlobalContext.Provider value={getContextByController(controller)}>
				<View
					key={`${meta.id}_${currentPath}`}
					state={state}
					handlers={handlers}
					actions={actions}
				/>
			</GlobalContext.Provider>
		)

		// KeepAlive 才把元素留在 views 里，否则用完即删
		if (controller.KeepAlive) {
			this.views[path] = view
		} else if (this.views.hasOwnProperty(path)) {
			delete this.views[path]
		}

		return view
	}
	render() {
		let { controller } = this.props
		return (
			<React.Fragment>
				{Object.keys(this.views).map(path => (
					<ViewItem
						key={path}
						path={path}
						isActive={path === controller.location.raw}
						view={this.renderView(path)}
						scrollY={this.scrollMap[path]}
						resetScrollOnMount={controller.resetScrollOnMount}
					/>
				))}
				<ControllerProxy
					key={controller.meta.id + controller.location.raw}
					controller={controller}
				/>
			</React.Fragment>
		)
	}
}
```


### KeepAlive 与 KeepAliveOnPush

两个开关，容易混：

| 配置 | 语义 |
| --- | --- |
| `KeepAlive = true` | 这个页面**永远**留在缓存池里，离开不 destroy，回来走 `restore` |
| `KeepAliveOnPush = true` | 只在「向前跳」时保活：`PUSH` 就 `saveToCache`，`POP` / `REPLACE` 就 `removeFromCache` |

```js
// bindStoreWithView 里的实现
let unlisten = history.listenBefore(location => {
  if (!this.KeepAliveOnPush) return
  if (location.action === 'PUSH') { this.saveToCache() }
  else { this.removeFromCache() }
})
```

典型用法：列表页开 `KeepAliveOnPush` —— 点进详情（PUSH）时保住列表的滚动位置和分页数据，从别处 `REPLACE` 进来则重新加载。

`saveToCache` / `removeFromCache` / `getAllCache` 在 Controller 基类里是**空实现**，真实逻辑由 create-app 的客户端包装类注入（服务端没有缓存概念，所以是空的）。

## 七、副作用的统一出入口：bindStoreWithView

客户端所有订阅都在这一个方法里挂上，并且**每一个都把反注册函数 push 进 `meta.unsubscribeList`**，`destroy()` 时统一清掉。服务端直接 `return`，一个监听都不挂。

```js
bindStoreWithView = () => {
    let { context, store, history, meta } = this
    if (!context.isClient || meta.isDestroyed) return    // 服务端不绑定

    // ① state 变化 → 刷新视图
    if (store) { ... store.subscribe(...) ... }

    // ② 路由跳转前，决定是否缓存当前页
    let unlisten = history.listenBefore(location => { ...KeepAliveOnPush... })
    meta.unsubscribeList.push(unlisten)

    // ③ 离开页面前的业务钩子
    if (this.pageWillLeave) {
      meta.unsubscribeList.push(history.listenBefore(this.pageWillLeave.bind(this)))
    }

    // ④ 关闭 / 刷新浏览器
    if (this.windowWillUnload) {
      meta.unsubscribeList.push(
        history.listenBeforeUnload(this.windowWillUnload.bind(this))
      )
    }
}
```

要点：

- `listenBefore` / `listenBeforeUnload` 是 **history v3 的 API**，v4 之后被移除了。imvc 用的 `create-history` 就是 history v3 的一个 TypeScript fork（仓库是 `Lucifier129/history`），所以它**不能换成官方 history v4/v5** —— 换了这两个钩子和 `location.raw` 全都没了。
- `restore()` 会**重新调一次 `bindStoreWithView`**，因为 `destroy()` 已经把订阅全退掉了。
- `meta.isDestroyed` 是防御性检查：异步回调回来时页面可能已经销毁。

## 八、CSS 预加载（preload）是怎么闭环的

目标：**首屏 CSS 内联进 HTML**，不额外发请求、不闪一下无样式内容；客户端接管时又不能重复拉一遍。

```
服务端 init 阶段
  fetchPreload() 逐个拉 preload 里声明的资源
     └─ 服务端用 context.serverPublicPath（本机地址）拉，不绕公网
     └─ 是 .css 就去掉所有 \r
     └─ 文本存进 context.preload[name]
              │
              ▼
  <Style name="main" />  渲染成 <style data-preload="main">...</style>
              │
              ▼  HTML 落到浏览器
  client.ts 启动时把这些 <style> 的内容读回来，塞进 appSettings.context.preload
              │
              ▼
  客户端 init 时 fetchPreload 发现 context.preload[name] 已存在 → 跳过，不重复请求
```

```js
// 客户端：动态收集服务端预加载的内容（src/entry/client.ts）
const preload = {}
Array.from(document.querySelectorAll('[data-preload]')).forEach(elem => {
  let name = elem.getAttribute('data-preload')
  preload[name] = elem.textContent || elem.innerHTML
})
appSettings.context.preload = preload

const app = createApp(appSettings)
```

```js
  /**
   * 预加载 css 样式等资源
   */
  fetchPreload = (preload) => {
    preload = preload || this.preload
    let keys = Object.keys(preload)
    if (keys.length === 0) return
    let { context } = this

    let list = keys.map(name => {
      if (context.preload[name]) return        // 服务端已经预加载过，直接跳过
      let url = preload[name]

      if (!_.isAbsoluteUrl(url)) {
        if (context.isServer) {
          url = context.serverPublicPath + url // 在服务端应请求本地的资源
        } else if (context.isClient) {
          url = context.publicPath + url
        }
      }

      return fetch(url)
        .then(_.toText)
        .then(content => {
          if (url.split('?')[0].indexOf('.css') !== -1) {
            /**
             * 如果是 CSS，清空回车符
             * 否则同构渲染时 react 计算 checksum 值会不一致
             */
            content = content.replace(/\r+/g, '')
          }
          context.preload[name] = content
        })
        .catch(error => {
          console.log(`preload resouce failed: ${name}`, error)
        })
    })
    return Promise.all(list)
  }
```

- **`\r` 必须清掉**：服务端读文件带 `\r\n`，客户端 hydrate 时字符串对不上，老版本 React 的 checksum 校验会失败并整棵树重绘。
- **失败只打日志不抛错**：预加载挂了页面还得能出来。
- v3 在这之上多了两件事：通过 webpack 的 `assets.json` 解析**带 hash 的真实文件名**，以及把 CSS 里的 `@public_path/` 占位符替换成实际 CDN 前缀。

## 九、同构的数据请求与跳转

### this.fetch

同一行 `this.fetch('/api/user')` 要在两端都能跑，差异被 Controller 吃掉了：

| 处理 | 说明 |
| --- | --- |
| `API` 映射 | 声明 `API = { user: '/api/user' }` 后可以写 `this.fetch('user')` |
| `restapi` 前缀 | 相对路径自动拼 `context.restapi`，服务端可用 `serverRestapi` 走内网 |
| **cookie 透传** | 浏览器会自动带 cookie，Node 不会 —— 所以服务端手动把 `context.req.headers.cookie` 塞进 headers |
| 默认值 | `method: 'GET'`、`credentials: 'include'`、`Content-Type: application/json` |
| `options.json !== false` | 自动 `.then(toJSON)`，非 200 直接 reject |
| `options.timeout` | 超时 reject，可配 `timeoutErrorFormatter` |

派生方法：`get(url, params, options)` 把 params 拼成 querystring，`post(url, data)` 自动 `JSON.stringify`。

### redirect 靠抛异常来中断

```
服务端                                  客户端
context.res.redirect(url)              绝对地址 → window.location.replace(url)
throw REDIRECT (一个 Symbol)            相对地址 → history.replace(url)
   │                                   如果 meta.isInitializing
   ▼                                      也 throw REDIRECT
init() catch 到 REDIRECT → return null      │
   │                                        ▼
create-app 拿到 null → 不渲染任何内容      中断当前 init，不再往下走
（createPageRouter 看到 content 为空直接 return）
```

这个设计的好处：`getInitialState` 里发现没登录，直接 `this.redirect('/login')` 就能**立刻终止后面的所有逻辑**，不用层层 return。

### 路由跳转与预取

- **Controller 上没有 `goto` / `back`**（v1 到 v3 都没有）。跳转用 `this.history.push / replace / goBack / goForward`，或者直接用 `<Link>` / `<NavLink>` 组件。
- `this.prefetch(url)` = `matcher(url)` + `loader(...)`，作用是**提前把目标路由的 JS chunk 拉下来**，不请求数据；匹配不到路由就返回 `null`。常见用法是在列表项曝光或 hover 时手动调一次，降低跳转白屏。

## 十、错误边界：靠劫持 React.createElement

React 的 ErrorBoundary 必须**包在出错组件的外面**，但业务不会到处手写 boundary。imvc 的做法很激进：只要 Controller 定义了 `errorDidCatch` 或 `getComponentFallback`，就在 `init()` 里把 `React.createElement` 换掉，**每个函数/类组件在创建时自动套一层 ErrorBoundary**。

```
init()
  ├─ 有 errorDidCatch / getComponentFallback ?
  │    └─ proxyHandler = proxyReactCreateElement(this)   // 换掉 React.createElement
  ├─ await initialize()
  │    出错 → errorDidCatch(error, 'controller') → getViewFallback() 或 <EmptyView/>
  └─ render() 时 proxyHandler.attach()

三种错误来源：
  'controller'  init / 生命周期钩子里抛的
  'model'       action 里抛的（store.actions 被逐个包了 try/catch）
  'view'        渲染时抛的（客户端在 viewEngine.render 里 catch，服务端在流的 error 事件里）
```

代价是**全局副作用**：服务端是长驻进程，改了 `React.createElement` 就必须还原，所以 `createPageRouter` 在 `finally` 和 stream `end` 里都会 `React.createElement = createElement`。这也是 imvc 服务端渲染最容易出诡异 bug 的地方。

## 十一、目录约定与构建

### 两个 "routes" 别搞混

| 配置 | 默认值 | 性质 | 作用 |
| --- | --- | --- | --- |
| `config.src` | `src/` | **同构** | index 模块默认导出页面路由表；每个页面一个文件夹，放 `Controller` / `View` / `Model` |
| `config.routes` | `routes/` | **仅服务端** | 同时是 express 的 views 目录（`layout: 'Layout'` → `routes/Layout.tsx`），也是注册自定义 express 中间件的地方 |

`config.routes` 的 index 模块里，**每一个导出都会被当成 `(app, server) => void | Promise<void>` 依次 await 执行**，并且全部注册在 `pageRouter` 之前 —— 所以自定义接口、鉴权中间件写在这里。自定义路由想回到 SSR 可以调 `res.renderPage`。

### 路由表的三种写法 = 三种加载时机

```ts
// src/index.ts
export default [
  { path: '/es6_module',  controller: ES6_Module },                    // 直接给类：打进主包
  { path: '/es6_dynamic', controller: import('./es6_dynamic/Controller') },   // 裸 promise：立即加载
  { path: '/static_view', controller: () => import('./static-view/Controller') }, // thunk：命中才加载
]
```

第三种（thunk）才是**代码分割点**，也是推荐写法；`loader` 拿到函数会先调用它再 `getModule` 解包 `.default`。`getFlatList` 会拍平嵌套数组，所以路由表可以按业务模块拆成多个文件再组合。**没有 `require.context`、没有文件系统路由**，路由必须显式声明。

### 构建

- webpack 配置只有一份 `createWebpackConfig(options, isServer)`，靠 `isServer` 分叉：客户端入口是 `react-imvc/entry/client`，服务端入口是项目的 `src/` 目录，输出 `publish/server.bundle.js`（`libraryTarget: 'commonjs2'`、`target: 'node'`、`nodeExternals`）。
- `alias['@routes'] = config.src`，这就是客户端入口能 `require('@routes')` 的原因。
- `webpack-manifest-plugin` 产出 `assets.json`，并额外生成**去掉扩展名的 key**，所以 Layout 里能写 `props.assets.vendor` / `props.assets.index` 拿到带 hash 的文件名；v3 的 `fetchPreload` 也靠它解析真实文件名。
- `optimization.splitChunks = { chunks: 'all', name: 'vendor' }`；生产环境客户端用 Terser（`drop_console: true`），服务端不压缩。
- 逃生舱：`config.webpackLoaders` / `config.webpackPlugins`，以及最后的 `config.webpack(result, isServer)` 直接改最终配置。
- 版本现状：**webpack 锁在 4.44.2**，`peerDependencies` 写了 React 17/18/19，但实际调用的是 React 17 的 `ReactDOM.hydrate`。

`imvc.config.js` 会被 Babel 转译后放进 `vm` 执行，再 `Object.assign({}, defaultConfig, config)`。常用项分四类：

| 分类 | 关键项 |
| --- | --- |
| 路径 | `root` `src` `routes` `layout` `publish` `static` `staticPath` `publicPath` `basename` `assetsPath` `serverBundleName` |
| 渲染 | `SSR` `renderMode` `serverRenderer` `context` `initialState` `appSettings` `restapi` `title/description/keywords/favicon` |
| 构建与开发 | `port` `devtool` `webpackDevMiddleware` `hot` `alias` `webpackPlugins` `webpackLoaders` `webpack` `useTypeCheck` `useSass` `useContentHash` `bundleAnalyzer` `compileNodeModules` |
| express | `helmet` `compression` `bodyParser` `cookieParser` `logger` `ReactViews` `staticOptions` |

TS 项目可以用框架导出的 `defineConfig()` 拿类型提示。

## 十二、v1 / v2 → v3 的关键差异

如果你手上的项目是老版本，下面这些点决定了网上的文章能不能照抄：

| 点 | v1 | v2 | v3 |
| --- | --- | --- | --- |
| `handlers` | 有：`combineHandlers` 把所有 `handleXxx` 方法收集后注入 View | 有 | **移除**，改用 `GlobalContext` + `connect` / `useCtrl` / `useModel` |
| View 收到的 props | `state` / `handlers` / `actions` | 同 v1 | 只有 `state` 和 `ctrl` |
| actions 合并顺序 | `{...actions, ...shareActions}` 内置赢 | 同 v1 | `{...shareActions, ...actions}` **你的赢**，且 `getFinalActions` 被 `await` |
| 函数式 `initialState` | 支持 `initialState(location, context)` | 支持 | **移除**，改用 `getInitialState` |
| 刷新节流 | 无，`subscribe` 里直接刷 | `debounce(5)` + `disableBatchRefresh` | 同 v2，另有 `flushSync` |
| `KeepAliveOnPush` | 无 | 有（比较字符串 `'PUSH'`） | 有（比较 `HistoryActions.PUSH` 枚举） |
| 错误边界 | 无 | 加入 `errorDidCatch` / fallback | 完整，另有 `viewWillHydrate`、`meta.isInitializing` |
| Early Hints | 无 | 有 `flushHeaders` | 有，可配 `earlyHintsLinks` / `disableEarlyHints` |
| 资源 hash | 直接拼路径 | 直接拼路径 | 读 webpack `assets.json`，支持 `@public_path/` 占位符 |

一直没变、也一直是「历史包袱」的部分：`ViewManager` 仍在用 `UNSAFE_componentWillReceiveProps`，客户端仍是 `ReactDOM.render` / `hydrate`，**没有迁到 React 18 的 `createRoot` / `hydrateRoot`**，所以 imvc 项目吃不到并发特性。

## 十三、服务端渲染的代价

SSR 的收益只有两个：**SEO** 和**首屏内容更快出来**。成本要一起算清楚：

- **多了一套服务**：构建、部署、监控、发布回滚都要覆盖 Node 侧，前端团队被迫承担运维。
- **服务器负载**：`renderToString` / `renderToNodeStream` 是 CPU 密集且**同步阻塞事件循环**的操作，流量大时 Node 单进程就是瓶颈，必须多进程 + 限流 + 降级（imvc 的 `SSR = false` 就是页面级降级开关）。
- **缓存难做**：外卖、本地生活这类业务「千人千面」—— 同一个 URL 不同地理位置/不同用户看到的内容不同，页面级缓存基本失效，只能退到片段缓存或数据层缓存。
- **同构约束会传染到业务代码**：不能在 `getInitialState` 里碰 `window`，Node 端不自动带 cookie，`initialState` 必须可 JSON 序列化，模块单例导致的跨请求污染（imvc 用 `deepCloneInitialState` 兜底）。
- **首屏快 ≠ 可交互快**：HTML 早到了，但 hydrate 之前点击是没反应的，TTI 可能反而变差。

所以判断要不要 SSR，看的是「是否需要 SEO」和「首屏内容是否是核心指标」，而不是技术上是否做得到。

## 面试速答

| 问题 | 答法 |
| --- | --- |
| imvc 的「同构」体现在哪 | 一个 Controller 类在两端各跑一次 `init()`；差异被基类和 `context.isServer/isClient` 吸收 |
| 服务端的 state 怎么传到客户端 | LayoutView 里 `JSON.stringify` 成 `window.__INITIAL_STATE__`，客户端 `initialize` 读到它就跳过 `getInitialState` 并走 `hydrate` |
| 为什么 `getInitialState` 不能用 `window` | 它主要在服务端执行；客户端只在**单页跳转**时执行，hydrate 时不执行 |
| 单页跳转为什么能保留滚动和输入 | 旧页面 DOM 没被卸载，只是 `display:none`；`ViewManager` 记了 `scrollMap`，controller 在缓存池里 |
| `KeepAlive` 和 `KeepAliveOnPush` 区别 | 前者永久保活，后者只在 `PUSH` 时保活、`POP`/`REPLACE` 时销毁 |
| relite 和 redux 区别 | action 就是 reducer `(state, payload) => newState`，自动 curry 成 `store.actions.X(payload)`，返回同一引用则不触发更新 |
| `redirect` 怎么中断后续逻辑 | 抛一个 `REDIRECT` Symbol，被 `init()` catch 后返回 `null`，上层不渲染 |
| CSS 预加载怎么避免重复请求 | 服务端把内容内联成 `<style data-preload>`，客户端启动时读回 `context.preload`，命中就跳过 fetch |
| 代码分割在哪一步发生 | 路由表里 `controller: () => import('...')` 这种 thunk 写法才是分割点，`loader` 命中路由时才调用它 |
| 异步逻辑放哪 | Controller 方法里（relite 的 action 只能同步），拿到数据再 `UPDATE_STATE` |
