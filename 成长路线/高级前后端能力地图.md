> 这份地图回答的不是「高级前端要背多少 API」，而是：**在大模型越来越强的前提下，什么能力仍然稀缺。**

## 判断标准的升级

旧标准：谁代码写得更快。

新标准：**谁能定义问题、做技术决策、设计系统、处理复杂约束，并对最终结果负责。**

大模型最容易替代的是**确定性、标准化、局部性**的编码工作；最难替代的是复杂系统里的**判断、权衡、架构、业务理解和工程责任**。

## 工作流的变化

```text
以前                        以后
需求                        需求
 ↓                           ↓
程序员设计                   人：定义问题 / 目标 / 约束
 ↓                           ↓
程序员写代码                 人：系统设计 / 技术决策
 ↓                           ↓
测试                        AI：生成大量代码
 ↓                           ↓
上线                        人：Review / 验证 / 调试
                             ↓
                            AI：继续修改
                             ↓
                            人：架构治理 / 性能 / 稳定性 / 风险
                             ↓
                            上线
```

结论一句话：**从「代码生产者」变成「系统设计者 + AI 驾驶员 + 工程负责人」。**

## 一、高级前端的 8 层

### ① JavaScript / TypeScript 深度

地基。不是 `map / filter / async-await` 会用，而是理解运行时与类型系统：

```text
JavaScript                      TypeScript
├── 执行上下文                  ├── 泛型
├── Event Loop                  ├── 类型体操
├── Microtask / Macrotask       ├── Structural Typing
├── Closure / GC                ├── 类型推导
├── Prototype                   ├── 类型守卫
├── Module                      ├── Declaration
└── 异步模型 / Runtime          └── Compiler
```

AI 能写出 `Promise.all(...)`，但下面这些要你自己判断：异步竞态为什么偶现？闭包为什么让内存无法释放？这个类型为什么推导成 `never`？

参考：[EventLoop](../Javascript/EventLoop.md)、[作用域、执行上下文](../Javascript/作用域、执行上下文.md)、[Promise](../ES6/Promise.md)、[TypeScript](../Typescript/index.md)

### ② 浏览器原理

普通前端和高级前端的分水岭。

```text
URL → DNS → TCP → TLS → HTTP
 → HTML → DOM / CSS → CSSOM
 → Render Tree → Layout → Paint → Composite → GPU
 ↑ 贯穿其中：Event Loop / JS Engine / Browser Process
```

应该能回答：页面为什么掉帧？5MB JSON 为什么让页面卡死？某个 CSS 为什么触发大量 Layout？为什么 Web Worker 能解决这个问题？`setTimeout` 为什么不准？

参考：[浏览器](../浏览器/浏览器.md)、[页面渲染过程](../HTTP/页面渲染过程.md)、[重排重绘](../CSS/重排重绘.md)、[计时器](../面试题/计时器.md)

### ③ 框架原理（React / Vue）

不停留在 `useState / useEffect / useMemo`，而是理解整条链路：

```text
React → Fiber → Scheduler → Render → Reconciliation → Commit → DOM
```

AI 很容易生成 `const [count, setCount] = useState(0)`，但很难替你决定：**这个状态到底该放组件里、URL 里、Context 里、外部 Store 还是服务端？** 技术选择本身比写代码重要。

参考：[Fiber](../React/Fiber.md)、[调度](../React/调度.md)、[react 原理](../React/react原理.md)、[性能优化](../React/性能优化.md)

### ④ 工程化 / 构建系统

不是「Webpack 配置背得熟」，而是理解构建管线：

```text
源码 → Parser → AST → Transform → Module Graph
 → Bundle → Code Split → Chunk → Minify → Browser
```

配套概念：Tree Shaking、Code Splitting、ESM/CJS、Source Map、Module Federation、Monorepo、构建缓存、CI/CD。这层不容易被完全替代，因为它牵扯整个工程体系而不是单个文件。

参考：[webpack 原理](../webpack/webpack原理.md)、[TreeShaking](../webpack/TreeShaking.md)、[打包工具对比](../webpack/打包工具对比.md)、[模块化](../模块化/模块化.md)

### ⑤ 性能工程

从「感觉页面很卡」升级到「**我能测出来为什么卡**」。

指标：FCP / LCP / CLS / INP / TTI / Long Task / Memory / CPU / Network / Bundle Size。

```text
用户反馈卡 → Performance 面板 → 发现 Long Task → CPU Profile
 → 找到 JS 热点 → 定位组件 → 改算法 / 渲染策略 → 重新压测
```

这条链路比「让 AI 帮我优化一下代码」高级得多。

参考：[性能时间](../性能/性能时间.md)、[浏览器性能](../性能/浏览器.md)、[项目性能优化](../性能/项目性能优化.md)、[浏览器插件与 CDP](../浏览器/浏览器插件与CDP.md)

### ⑥ 网络与安全

HTTP / HTTPS / TCP / DNS / WebSocket / SSE / HTTP2 / HTTP3 / CDN / Cache / Cookie / CORS / CSRF / XSS / CSP / JWT / OAuth。

自检题：**输入 URL 到页面出现，中间发生了什么？** 能从浏览器一路讲到网络和服务器，就已经进入高级范畴。

参考：[HTTP](../HTTP/HTTP.md)、[网络安全](../HTTP/网络安全.md)、[前端缓存](../HTTP/前端缓存.md)、[TCP&UDP](../HTTP/TCP&UDP.md)

### ⑦ 前端架构能力

以低代码 / 工作卡这类平台为例，要分层去想：

```text
工作卡
├── 协议层（Schema）
├── Renderer
├── Component
├── Layout / Event / State / Data
├── PC / Mobile
└── Server Driven
```

需要回答的是设计问题：协议怎么设计？旧版本怎么兼容？多端怎么复用？组件怎么扩展？插件化怎么做？SDK 怎么设计？业务接入成本怎么降？

这类工作 AI 很难独立完成——它依赖大量上下文和组织约束。

参考：[微前端原理](../微前端/原理.md)、[设计模式](../Javascript/设计模式.md)、[运行时动态执行代码](../模块化/运行时动态执行代码.md)

### ⑧ AI 原生前端

不只是「用 Cursor / Claude 写代码」，而是理解并能落地这条链：

```text
LLM → Prompt → Tool Calling → Agent → Context → RAG → Memory → Evaluation → Engineering System
```

落到工作卡这类场景：

```text
用户自然语言 → Agent → 理解卡片结构 → Tool Calling → 生成 Ops
 → Schema 校验 → 后端 Apply → Renderer 渲染 → 结果验证 → 自动修复
```

这已经不是传统前端了。

## 二、高级后端的 8 层

主线：`Java → JVM → 并发 → DB → 缓存 → MQ → RPC → 分布式 → 架构`。

### ① Java / JVM

不只会 `List / Map / Stream / Spring`，而是理解 Heap、Stack、Metaspace、GC、ClassLoader、JIT、Thread；能讲清「一个 Java 请求是怎么跑起来的」。

### ② 并发编程

```text
Thread → ThreadPool → synchronized → Lock → CAS → Atomic → volatile → ConcurrentHashMap
高并发手段：限流 / 削峰 / 异步 / MQ / 缓存 / 连接池 / 线程池
```

高级问题是「10000 QPS 来了怎么办」，而不是「ThreadPoolExecutor 怎么创建」。

参考：[高并发](../性能/高并发.md)

### ③ 数据库

```text
MySQL
├── Index / B+ Tree
├── Transaction / MVCC / Lock / Isolation
└── Redo Log / Undo Log / Binlog
```

要能解决：这个 SQL 为什么慢？为什么死锁？为什么索引没生效？数据库 CPU 100% 怎么查？1000 万数据怎么查？

参考：[数据库](../java/数据库.md)

### ④ 缓存 / Redis

不是 `get/set`，而是：缓存命中率、穿透、击穿、雪崩、一致性、分布式锁、热点 Key。

参考：[缓存对比](../Javascript/缓存对比.md)

### ⑤ 消息队列

Kafka / RocketMQ / RabbitMQ 的共同问题域：消息可靠性、重复、丢失、消费失败与重试、顺序消息、幂等、积压处理。

### ⑥ RPC / 微服务

服务发现、负载均衡、超时、重试、熔断、降级、限流、幂等。从这里开始真正进入分布式系统。

### ⑦ 分布式系统

```text
CAP / BASE / 一致性 / 分布式锁 / 分布式事务
Leader Election / Raft / Consensus / Idempotency / Fault Tolerance
```

思维方式变了：以前问「代码能不能跑」，现在问「**机器挂了怎么办？网络断了怎么办？请求重试两次怎么办？数据库提交成功但服务挂了怎么办？**」

### ⑧ 系统架构

```text
需求 → 业务模型 → 系统边界 → 服务拆分 → 数据模型
 → 技术选型 → 容量评估 → 性能 → 可靠性 → 成本
```

以「设计一个 10 万 QPS 的订单系统」为例：AI 能生成代码，但为什么这么拆、库表怎么设计、Redis 和 MQ 放在哪、哪里必须强一致、哪里可以最终一致、单机 QPS 多少、要多少机器、故障怎么兜——这些才是核心。

## 三、真正不容易被 AI 替代的 7 项能力

| 能力 | 普通开发 | 高级开发 |
| --- | --- | --- |
| ① 问题定义 | 产品说什么就写什么 | 先判断产品真正要解决的问题 |
| ② 架构设计 | 这个函数怎么写 | 整个系统应该怎么设计 |
| ③ 技术选型 | 知道 API | 知道**为什么选它**（Redis/MySQL/MQ/RPC/WebSocket/SSE…） |
| ④ 性能与容量 | 感觉慢 | 从 QPS→RT→并发→CPU→内存→DB→网络 推导瓶颈 |
| ⑤ 故障处理 | 正常路径能跑 | 机器挂 / 网断 / DB 挂 / MQ 积压 / 请求重复 / LLM 超时 / Tool 失败怎么办 |
| ⑥ 跨领域 | 纯前端或纯后端 | Frontend + Backend + Infra + AI + Product 打通 |
| ⑦ AI 驾驭 | 自己写代码 | 设计系统 → 指挥 AI → Review → 验证 → 优化 |

第 ⑥ 项具体说：**能把一个用户请求一路追到 CPU / JVM / DB / Redis / 网络 / 浏览器的人**，最稀缺。

竞争力的迁移路径：`Coding Skill → Engineering Skill + System Thinking + AI Skill`。

## 四、结合我自身的路线选择

现有基础偏前端 + AI：React / TypeScript / 浏览器 / 低代码 / 工作卡 / Agent / Tool Calling / RAG。因此**不适合把自己重塑成一个传统 Java 后端**，更高价值的方向是 AI 应用架构 / Agent Engineer：

```text
             AI 应用架构师 / AI Agent Engineer
                         │
             ┌───────────┴───────────┐
             ↓                       ↓
         Frontend                 Backend
      Browser 原理              Java / JVM
      React 原理                并发
      工程化                    MySQL
      性能                      Redis
      可视化 / Low-code         MQ / RPC
             └───────────┬───────────┘
                         ↓
                    AI Agent
                         ↓
                 Tool / RAG / MCP
                         ↓
                  AI Native System
```

工作卡的「AI 局部修改」已经在这条路上：自然语言 → LLM → Tool Calling → 结构化 Schema → Ops → 后端 Apply → 前端 Renderer → 结果验证 → 自动修复。

## 五、能力分层

```text
L1 会写代码        ← AI 最容易替代
L2 会用框架        ← AI 最容易替代
L3 会解决复杂问题   ← AI 变成助手
L4 会做系统设计
L5 会做架构与技术决策
L6 会用 AI 放大工程能力  ← AI 是杠杆
L7 能设计 AI Native 系统 ← AI 是杠杆
```

L5～L7 的人反而因为 AI 获得巨大杠杆：一个人能完成过去一个小团队的开发、测试、重构和系统搭建。

## 六、给自己的一句话结论

值得投入的不是继续堆「前端 API 数量」，而是打通这条链：

> **浏览器原理 → Node → Java/JVM → 并发 → DB/Redis/MQ → RPC/分布式 → AI Agent → 系统架构**

链路一通，就从「前端开发」变成能**从 UI 一直看到操作系统、后端、基础设施和 AI Agent** 的全栈型工程师。
