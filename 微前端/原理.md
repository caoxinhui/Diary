# 微前端 原理

### 微前端要解决什么

一句话：**把一个巨型单页应用按业务垂直拆开，每个子应用可独立开发、独立部署、甚至独立技术栈，运行时再由一个主应用（基座）拼回一个 SPA。**

关键词是"运行时拼装"，这也是它和邻居方案的分界线：

| 方案 | 拼装时机 | 代价 |
| --- | --- | --- |
| Monorepo + npm 包 | 编译期 | 子应用改一行，基座得重新构建发布 |
| iframe | 运行时 | 隔离最彻底，但路由、弹窗、通信、白屏全是问题 |
| 微前端（single-spa / qiankun） | 运行时 | 同一个 document，路由调度和沙箱都得自己造 |
| Module Federation | 运行时加载 + 编译期约定 | 共享依赖版本要对齐，本质是"跨应用共享模块"而不是"应用编排" |

「同一个 document + 运行时拼装」直接推出了三个必须自己解决的问题，也正是面试必问的三点：**谁在什么时候把哪个子应用挂上去（路由）**、**子应用的全局变量怎么不打架（JS 隔离）**、**样式怎么不互相覆盖（CSS 隔离）**。

下面的实现细节以 single-spa / qiankun 为例（single-spa 本身是什么见最后一节）。

## 一、路由原理

> 前置知识：单个 SPA 自己的路由是怎么跑起来的，见 [SPA路由原理.md](SPA路由原理.md)。微前端路由是同一套手法，只是匹配结果从"渲染哪个组件"变成"挂载哪个应用"。

### 两级路由

```
浏览器 URL: /app1/detail/1
                │
       ┌────────┴──── 第一级 · 主应用路由：URL → 哪些子应用该活着
       │               activeWhen: loc => loc.pathname.startsWith('/app1')
       ▼
   load(app1) → bootstrap → mount(container)
                │
                └────── 第二级 · 子应用路由：/detail/1 → 渲染哪个页面组件
                        子应用自己的 react-router / vue-router，base = '/app1'
```

主应用**只做"应用级"分发**，不关心子应用内部有几个页面；子应用路由必须配 `base`（`basename: '/app1'`、`createWebHistory('/app1')`），否则两级路由会去抢同一段 pathname，表现为白屏或死循环重定向。

### 为什么必须劫持 history

浏览器对 URL 变化的通知是**不完整的**：

| 行为 | 有没有事件 |
| --- | --- |
| 用户点前进 / 后退，`history.go/back/forward` | ✅ `popstate` |
| hash 变化 | ✅ `hashchange` |
| `history.pushState()` / `replaceState()` | ❌ **什么都不派发** |

而 SPA 内部跳转 99% 走 `pushState`。所以框架必须自己把这个缺口补上：

```js
// 1. 原生就有事件的，直接监听
window.addEventListener('hashchange', urlReroute);
window.addEventListener('popstate', urlReroute);

// 2. pushState / replaceState：包一层，改完 URL 手动补派发一个 popstate
function patchedUpdateState(updateState) {
  return function () {
    const urlBefore = window.location.href;
    const result = updateState.apply(this, arguments);
    const urlAfter = window.location.href;
    if (urlBefore !== urlAfter) {
      // 伪造事件，让 pushState 走和后退按钮完全相同的那条 reroute 通道
      window.dispatchEvent(new PopStateEvent('popstate', { state: window.history.state }));
    }
    return result;
  };
}
window.history.pushState = patchedUpdateState(window.history.pushState);
window.history.replaceState = patchedUpdateState(window.history.replaceState);
```

**所有路由方案的地基都是这一步**：把 5 种 URL 变化方式归一成一个 `reroute()` 入口。

### 劫持 addEventListener：最容易被追问的一点

子应用的路由库自己也监听 `popstate`。如果放任不管，URL 一变，**正在被卸载的子应用的监听器也会被触发**——它会拿着一个已经不属于自己的 URL 去匹配路由、去 setState，结果就是报错或者页面闪一下旧内容。

single-spa 的解法是把这类监听器"截留"下来，由自己决定什么时候调：

```js
const routingEventsListeningTo = ['hashchange', 'popstate'];
const originalAddEventListener = window.addEventListener;

window.addEventListener = function (eventName, fn) {
  if (typeof fn === 'function' && routingEventsListeningTo.includes(eventName)) {
    capturedEventListeners[eventName].push(fn); // 存起来，不真正挂到 window 上
    return;                                     // 提前 return
  }
  return originalAddEventListener.apply(this, arguments);
};
```

于是 `reroute` 的执行顺序变成：

```
URL 变化（点击 / pushState / 后退 / hash）
   │
   ▼ urlReroute()
 diff 出四组应用：toUnload / toUnmount / toLoad / toMount
   │
   ├─ 1. 先 unmount 掉不该活着的应用
   │
   ├─ 2. 此刻 URL 才"可信"，统一补发被截留的 popstate / hashchange 监听器
   │        → 存活下来的子应用路由此时才响应新 URL
   │
   └─ 3. 再 load → bootstrap → mount 新应用
```

一句话记住：**先卸旧 → 再通知路由 → 后挂新**，保证任何时刻监听器看到的 URL 都归自己管。

### activeWhen 与生命周期状态机

主应用侧的匹配规则就是一个纯函数 `(location) => boolean`：

```js
registerApplication({
  name: 'app1',
  app: () => import('./app1/main.js'),      // loading function，返回生命周期对象
  activeWhen: '/app1',                       // 等价于 loc => loc.pathname.startsWith('/app1')
  customProps: { token },
});
```

每个子应用是一个状态机，`reroute` 干的事就是推动状态迁移：

```
NOT_LOADED → LOADING_SOURCE_CODE → NOT_BOOTSTRAPPED → BOOTSTRAPPING
   → NOT_MOUNTED ⇄ (MOUNTING → MOUNTED → UNMOUNTING) → UNLOADING → NOT_LOADED
                              ↘ 任一步抛错 → SKIP_BECAUSE_BROKEN / LOAD_ERROR
```

注意 `bootstrap` 只在首次挂载前跑一次，而 `mount / unmount` 会随路由反复来回，所以**副作用清理必须写在 `unmount` 里**，不能指望 `bootstrap` 的对称。

### 路由这块常见的坑

| 现象 | 原因 |
| --- | --- |
| 刷新子应用路由 404 | 服务端没配 history fallback，`/app1/**` 要全部回落到基座的 index.html |
| 子应用页面渲染两次 / 抖动 | 子应用路由没配 `base`，主子两级路由同时匹配 |
| 主子应用都用 hash 时互相抢 | 一个 URL 只有一个 hash，主应用用 history、子应用用 hash（或反之）才不冲突 |
| 子应用里 `pushState` 不生效 | 沙箱把 `history` 也代理了，或子应用自己又劫持了一次 `pushState` |

## 二、JS 资源隔离原理

### 问题的本质

所有子应用跑在同一个 `window` 上，于是：`window.$`、`window.React` 互相覆盖；子应用 A 注册的 `setInterval`、`window.addEventListener` 在卸载后还在跑；两个子应用都读写 `window.__APP_STATE__`。

隔离的核心思路只有一句：**给每个子应用一个假的 `window`，让它以为自己独占全局。**

### 怎么把假 window 塞给子应用

子应用代码是一段字符串（HTML Entry 取到的 `<script>` 内容），执行前包一层：

```js
// import-html-entry 的产物大致长这样
;(function (window, self, globalThis) {   // ① 三个形参遮蔽全局标识符
  with (window) {                         // ② 作用域欺骗
    /* 子应用源码 */
  }
}).bind(proxy)                            // ③ 绑 this
  (proxy, proxy, proxy);                  // ④ 传参
```

**四个 `proxy` 是同一个对象**，就是下文 ProxySandbox 里那个 `new Proxy(fakeWindow, ...)`，写四次只因为要塞进四个不同入口：`.bind(proxy)` 决定函数体内 `this` 的值，后面三个实参依次赋给形参 `window / self / globalThis`。`bind` 的首参只是 thisArg，不占形参位，所以 `.bind(proxy)(a,b,c)` 等价于 `.call(proxy,a,b,c)`。子应用无论从哪条路摸"全局对象"，摸到的都是同一个假 window。

**① 为什么形参是这三个名字**：形参本质是函数作用域内的局部变量，参数名叫 `window`，就等于把外层真正的 `window` 遮蔽（shadow）掉了。浏览器里拿全局对象只有这三种写法，且都真实出现在打包产物里——`window` 是业务代码最常见的写法；`self` 是 UMD 头部和 Worker 兼容写法，**webpack 5 注册异步 chunk 用的就是 `self["webpackChunkxxx"]`**；`globalThis` 是 ES2020 标准写法，新工具链和 polyfill 在用。漏掉任何一个都会破防。

**③ `.bind(proxy)` 给 `this` 兜底**：非严格模式下 `f()` 这种普通调用里 `this` 是真正的全局对象，UMD 头部的 `typeof self !== 'undefined' ? self : this`、顶层的 `this.MyLib = {}` 都靠它导向 proxy。但 `bind` 只管这一层函数——子应用里嵌套的非严格函数被裸调用（经典的 `(function () { return this })()`）拿到的仍然是真 window，这是 Proxy 沙箱公认的漏点之一。

**② `with` 干了什么**：`with (obj) { ... }` 把 `obj` **压入作用域链**，块内出现的裸标识符（不带 `obj.` 前缀的 `foo`、`setTimeout`）会先当作 `obj` 的属性去找。查一个裸标识符的完整顺序是：

1. **with 块自身的词法环境** —— 块内的 `let` / `const` / `class` / `function` 声明住在这里
2. **with 的对象环境** —— 先问 `has(proxy, 'foo')`：`true` 则后续读写走 `get` / `set` trap，`false` 则继续往外找
3. 函数作用域 —— `window` / `self` / `globalThis` 三个形参，以及源码里的 `var` 声明
4. 外层作用域 → 真正的全局对象

`has` 必须返回 `true` 是这里最技术性的一点：`with` 查标识符时会先问 `has`，返回 `false` 就跳到第 3、4 步找真 window，隔离直接漏底。

由此带来一个容易被追问的差异——**不同声明形式的归属不一样**：

```js
with (proxy) {
  var a = 1;       // 声明提升到函数作用域，但赋值走第 2 步 → 写进 fakeWindow ✅
  b = 2;           // 裸赋值，同上 → 写进 fakeWindow ✅
  let c = 3;       // 住在第 1 步的块作用域，proxy 完全看不到
  function d() {}  // 同上，块作用域
  setTimeout(fn);  // 读走 get trap → 拿到被 patch 过的版本 ✅
}
```

`var` 和裸赋值落进假 window，正好复刻了"真实脚本里顶层 `var` 会变成 window 属性"的语义；`let` / `const` / `function` 留在块作用域里，等于子应用的模块级变量天然私有，本来就不会冲突。

四个手段叠在一起才够严密：

| 手段 | 挡住什么写法 |
| --- | --- |
| 形参 `window / self / globalThis` 遮蔽 | `window.foo = 1`、`self.webpackChunk = []`、`globalThis.foo` |
| `.bind(proxy)` | 非严格模式下顶层的 `this.foo` |
| `with (proxy)` | **裸变量** `foo = 1`、`var foo = 1`、`setTimeout(...)` |
| Proxy 的 `has` trap 恒返回 true | 让 `with` 不会因为"属性不存在"而穿透到外层作用域 |

### 这段包裹代码的工程细节

- **开头那个 `;`**：多段 script 拼接执行时，防止上一段末尾缺分号被 ASI 接成函数调用。同理源码末尾会补一个 `\n`，避免最后一行是 `//` 注释时把闭合的 `}` 一起注释掉。
- **子应用里的 `'use strict'` 会失效**：指令序言必须位于函数体/脚本的最开头才生效，源码被塞进 `with` 的块里之后，它只是一条普通的字符串表达式语句。这既是"`with` 不报 SyntaxError"的原因（严格模式下 `with` 是语法错误），也是为什么还得靠 `.bind` 去兜非严格模式的 `this`。
- **`with` 的代价**：带 `with` 的作用域 V8 无法做静态分析，优化直接放弃，且每个裸标识符访问都要过一次 `has` + 一次 `get`。qiankun 的应对是用 `Symbol.unscopables` 把一批必然不需要代理的内置名（`Array`、`Object`、`Promise`、`Math`…）声明为"逃出 `with` 块"，直接解析到原生对象。
- **`with` 只在多实例沙箱里出现**：单例沙箱（LegacySandbox）本来就写真 window，裸变量落到真 window 符合预期，只需要形参 + `bind`；只有 ProxySandbox 这种必须截住裸变量的场景才加 `with`。
- **ESM 进不来**：这套包裹是用 `eval` / `new Function` 执行字符串，函数体里不能出现 `import` / `export` 语句，所以子应用产物得是 UMD 或 SystemJS 格式。真用原生 `<script type="module">`，这层沙箱直接被绕过去。

> 同样是 `new Function` + 形参注入，但目标是"拿到导出物"而不是"拦住全局写入"时（低代码 / AI 动态组件），构造方式见 [模块化/运行时动态执行代码.md](../模块化/运行时动态执行代码.md)。

### 三种沙箱的演进（qiankun）

| 沙箱 | 原理 | 多实例 | 用在哪 |
| --- | --- | --- | --- |
| **SnapshotSandbox** 快照沙箱 | 激活时遍历 window 存快照，失活时 diff 并还原、记下自己改过的 key，下次激活再写回 | ❌ 单例 | 不支持 Proxy 的老浏览器兜底 |
| **LegacySandbox** 单例代理 | 用 Proxy，但仍然写真 window；只额外记三张表（新增的 / 改过的原值 / 当前值），还原时 O(改动数) 而不是 O(window 属性数) | ❌ 单例 | `singular: true` |
| **ProxySandbox** 多例代理 | 每个应用一个 `fakeWindow`；`get` 先查 fake 再回落真 window，`set` **只写 fake** | ✅ | 默认，多个子应用同屏共存 |

ProxySandbox 的关键代码骨架：

```js
const rawWindow = window;
const fakeWindow = {};
const proxy = new Proxy(fakeWindow, {
  set(target, p, value) { target[p] = value; return true; },        // 只污染自己
  get(target, p) {
    if (p in target) return target[p];
    const v = rawWindow[p];
    // document / addEventListener 这类必须绑回原 window，否则 Illegal invocation
    return typeof v === 'function' && !isConstructable(v) ? v.bind(rawWindow) : v;
  },
  has() { return true; },                                          // 供 with 使用
});
```

### 光有 Proxy 不够：还得打补丁清副作用

变量隔离只解决了"命名冲突"，没解决"卸载后残留"。所以沙箱激活时还会 patch 一批 API，失活时统一回收：

| patch 的对象 | 记录什么 | unmount 时做什么 |
| --- | --- | --- |
| `setTimeout` / `setInterval` | 返回的 timer id | 全部 `clearTimeout / clearInterval` |
| `window.addEventListener` | (type, fn) 列表 | 全部 `removeEventListener` |
| `document.head/body.appendChild / insertBefore` | 动态插入的 `<script>` / `<style>` / `<link>` | script 交给沙箱执行；style 挂到子应用容器上并在卸载时移除 |
| `window.fetch` / XHR（可选） | 请求 | 卸载时 abort，避免回调打到已销毁的组件 |

其中动态 `appendChild` 的劫持是必需项：子应用里 `import()` 出来的异步 chunk、按需加载的组件库样式，都是运行时往 `document.head` 插节点的，不劫持就既逃出沙箱又留不下清理线索。

### 沙箱隔离不了的东西（务必主动说）

Proxy 沙箱是**逻辑隔离，不是安全隔离**：

- **共享存储**：`localStorage` / `sessionStorage` / `cookie` / IndexedDB 仍然同源共享，只能靠 key 前缀约定
- **原型链污染**：`Array.prototype.xxx = ...`、`Object.prototype` 被改，所有应用一起中招
- **DOM 是共享的**：`document.body.innerHTML = ''` 谁都拦不住
- **稳定性不隔离**：一个子应用死循环 / OOM，整个页面一起卡死
- **`window` 上的 getter/setter、不可配置属性**、以及某些原生对象 `instanceof` 判断会在跨 realm 时失真
- 想要真隔离只有换赛道：**iframe**（天然独立 realm + 独立 history）、Web Worker、或未来的 ShadowRealm

这也是 **wujie（无界）** 的思路：用 iframe 跑 JS（白送沙箱和 history），用 Web Component + Shadow DOM 在主文档里承载 DOM，绕开 iframe 的弹窗和白屏问题；**micro-app** 则是 Web Component + 自研沙箱。

## 三、CSS 资源隔离原理

CSS 天生是全局的，冲突有两类，要分开答：

- **时序冲突**：A 卸载了但它的 `<style>` 还留在 head，切到 B 之后继续生效
- **共存冲突**：A、B 同屏，两边都有 `.btn { }` 或都引了不同版本的组件库

### 方案对比

| 方案 | 原理 | 隔离度 | 主要坑 |
| --- | --- | --- | --- |
| **卸载时移除 style** | 记录子应用插入的 `style/link`，unmount 时摘掉、remount 时还原（qiankun 默认行为） | 只解时序冲突 | 同屏共存无效 |
| **Shadow DOM**<br>`strictStyleIsolation: true` | `container.attachShadow({ mode: 'open' })`，样式作用域天然封闭 | 最强（不含 iframe） | 见下 |
| **运行时改写选择器**<br>`experimentalStyleIsolation: true` | 解析 CSSOM，给每条规则加前缀：`.btn` → `div[data-qiankun="app1"] .btn`；`body/html/:root` 替换成容器选择器 | 够用 | `@keyframes`/`@font-face` 无法加前缀；`@media`/`@supports` 要递归处理；有运行时开销 |
| **构建期约定** | CSS Modules / BEM / postcss 加前缀 + 组件库 `prefixCls`（antd `ConfigProvider`、element `namespace`） | 强且零运行时成本 | 要改子应用构建，做不到"接入任意存量应用" |
| **iframe** | 独立文档 | 彻底 | 路由、弹窗定位、通信、白屏 |

### Shadow DOM 为什么"看起来完美却少有人敢用"

隔离是双向的，样式进不来，**依赖全局 document 的东西也出不去**：

- 挂到 `document.body` 的**弹窗/下拉/tooltip 跑到 Shadow 外面，样式全丢**（antd Modal、Select、DatePicker 是重灾区）。绕法：`getPopupContainer={node => node.parentNode}`、`ConfigProvider` 统一指定容器
- 第三方库的 `document.querySelector` / `document.getElementById` 拿不到 Shadow 内的节点
- 事件冒泡到外层时 `event.target` 被 **retarget** 成宿主元素，外部的事件委托失效
- `document.activeElement`、`@font-face`、SVG `url(#id)` 引用都会有额外坑

**工程上最实用的组合**：构建期前缀（组件库 `prefixCls` + postcss 前缀）解决共存冲突 + 卸载移除 style 解决时序冲突，Shadow DOM 只在接入完全不可控的第三方应用时才考虑。

## 四、single-spa 是什么

### 定位

**single-spa 是微前端的"顶层路由 + 生命周期调度器"，只有几百行核心逻辑，别的什么都不管。**

| single-spa 做 | single-spa 不做 |
| --- | --- |
| 劫持 history / 监听 popstate，统一成 `reroute` | ❌ 加载资源（`app` 参数是你自己写的 loading function，一般配 SystemJS / Import Maps / 动态 `import()`） |
| 用 `activeWhen` 判断哪些应用该活着 | ❌ JS 沙箱 |
| 驱动 `bootstrap / mount / unmount` 状态机 | ❌ CSS 隔离 |
| 保证卸载与挂载的时序、错误隔离 | ❌ 应用间通信、预加载 |

所以它更像一份**协议**：子应用只要导出约定的生命周期函数，用什么框架都行。

### 子应用协议

```js
// 子应用入口必须导出这三个（返回 Promise），可选 unload / update
export async function bootstrap(props) { /* 只跑一次：初始化 */ }
export async function mount(props) {
  // props: { name, singleSpa, mountParcel, domElement / container, ...customProps }
```

### 30 行手写一个 mini single-spa

```js
const apps = [];
export function registerApplication(app) {
  apps.push({ ...app, status: 'NOT_LOADED', lifecycles: null });
}

const isActive = (app) => app.activeWhen(window.location);

async function reroute() {
  const toUnmount = apps.filter((a) => a.status === 'MOUNTED' && !isActive(a));
  const toMount   = apps.filter((a) => a.status !== 'MOUNTED' && isActive(a));

  // 1. 先卸旧
  await Promise.all(toUnmount.map(async (a) => {
    await a.lifecycles.unmount({ name: a.name });
    a.status = 'NOT_MOUNTED';
  }));

  // 2. 补发被截留的路由监听器（这里省略 capturedEventListeners 的实现）
  flushCapturedEventListeners();

  // 3. 再挂新
  await Promise.all(toMount.map(async (a) => {
    if (a.status === 'NOT_LOADED') {
      a.lifecycles = await a.app();                     // load
      await a.lifecycles.bootstrap({ name: a.name });    // 只跑一次
    }
    await a.lifecycles.mount({ name: a.name });
    a.status = 'MOUNTED';
  }));
}

// 把 5 种 URL 变化归一到 reroute
window.addEventListener('popstate', reroute);
window.addEventListener('hashchange', reroute);
['pushState', 'replaceState'].forEach((k) => {
  const raw = history[k];
  history[k] = function (...args) {
    const before = location.href;
    const r = raw.apply(this, args);
    if (before !== location.href) window.dispatchEvent(new PopStateEvent('popstate'));
    return r;
  };
});

export const start = reroute;
```

### qiankun 在 single-spa 之上加了什么

qiankun = single-spa（路由与生命周期）+ 一整套工程化补齐：

| 能力 | 实现 |
| --- | --- |
| **HTML Entry** | `import-html-entry` 拉子应用的 index.html，解析出 `<script>` / `<style>` 并自己执行，子应用几乎零改造（single-spa 是 JS Entry，得手动导出生命周期 + 打成 umd） |
| **JS 沙箱** | SnapshotSandbox / LegacySandbox / ProxySandbox + 定时器、事件、动态 append 的 patch |
| **CSS 隔离** | 卸载移除 style、`strictStyleIsolation`、`experimentalStyleIsolation` |
| **预加载** | `prefetch` 在浏览器空闲时提前拉子应用静态资源 |
| **通信** | `initGlobalState` 提供的发布订阅（props 下发 + onGlobalStateChange） |

一句话对比：**single-spa 是内核，qiankun 是开箱即用的发行版**；wujie / micro-app 则是在"隔离方式"上换了实现（iframe + Shadow DOM / Web Component）。

### 面试速答版

- **路由**：微前端路由是两级的。主应用把 `popstate` / `hashchange` 加上被劫持的 `pushState` / `replaceState` 归一成一个 `reroute()`，用 `activeWhen` diff 出该卸载和该挂载的应用，按「先 unmount 旧 → 补发被截留的路由监听器 → 再 mount 新」的顺序推进状态机；子应用路由配 `base` 只管自己那一段。
- **JS 隔离**：给每个子应用一个 Proxy 假 `window`，通过 `(function(window, self, globalThis){ with(window){...} }).bind(proxy)` 注入，`set` 只落到 fakeWindow 上实现多实例；再 patch 定时器 / 事件 / 动态 appendChild，在 `unmount` 时统一回收。本质是逻辑隔离，storage、原型链、DOM、稳定性都不隔离，要彻底隔离得用 iframe。
- **CSS 隔离**：区分时序冲突（卸载时移除 style 即可）和共存冲突（运行时给选择器加容器前缀，或 Shadow DOM，或构建期 prefixCls / postcss 前缀）。Shadow DOM 最彻底但会让挂到 body 的弹窗失去样式，生产上更常用构建期前缀。
- **single-spa**：只做路由调度 + 生命周期协议（`bootstrap` / `mount` / `unmount`）的微前端内核，不管资源加载和隔离；qiankun 在它之上补了 HTML Entry、沙箱、样式隔离、预加载和通信。
